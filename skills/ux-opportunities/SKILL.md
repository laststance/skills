# UX Opportunities

Start with the user's app and an open question. Finish with up to three decisions the owner can make from a local before-and-after HTML report. Write the report and chat in the requester's language. The target may be a web, desktop, or mobile app.

## Review

1. **Understand the job.** Use the current project when no target is named. Read the product brief and design conventions if available. Identify who opens the app, what they came to accomplish, and what success looks like. Choose the consequential journeys after surveying the main surfaces. Ask only if different audiences or goals would materially change the review and the supplied evidence cannot resolve them.
2. **Retrieve prior work.** Follow the [notebook protocol](references/notebook.md) to load this project's history and search the personal library by user task. Use the full decision trail, including declines and worse outcomes. On a repeat review, offer one optional, grouped follow-up about pending proposals while continuing the review. In a non-interactive run, include that invitation once in the report. Repeat a proposal only when you can explain what changed since the previous decision.
3. **Observe the current journey.** Follow the app from intention through completion or recovery using the available browser, desktop, or device surface. Use a fixture for actions that would change real data. With supplied screenshots, videos, or source alone, identify which states are visible and which transitions remain unknown. Record what the interface actually does and keep predicted user reactions and frequency estimates explicit as hypotheses.
4. **Find comparable work.** Look for a direct competitor or the closest product serving the same job, and a product from another domain handling the same interaction. Choose by task, constraints, and platform. Inspect the actual flow, an official help page, a recording, or a screen collection such as Mobbin when available. Record the product, precise source, observation date, behavior, and the conditions under which it may transfer. A search snippet or a remembered reputation is a lead. When research is limited, report the gap and qualify any proposal that relies on it.
5. **Rank changes by obstruction to the user's goal.** Consider adding a capability, moving an existing control, and removing a step or element. Keep only supported opportunities. Lead with blocked completion, poor recovery, or recurring friction where the evidence warrants it. For each, connect the observed obstacle to a specific change, the relevant reference or negative precedent, the predicted benefit, and a check that could disprove it. If no change clears that bar, show what was checked and what evidence would help.
6. **Deliver and remember.** Use the [report starter](assets/report.html). Show a recognizable current screen beside an annotated proposal, or paired screen-level wireframes. Include before/after steps when the flow changes. Label a reconstruction, proposed UI, and untested outcome in the report language. Keep navigation and labels usable on narrow screens. Use public source links. Embed only case-appropriate imagery and keep the report readable offline. Save the report, its ranked titles and tags, and the market observations with the notebook. Open the saved HTML locally or verify it in an available browser, return its path, and name the first decision to make. Implementation of the target app is a separate task.

## Feedback

For `/ux-opportunities feedback <proposal-id> <comment>`, use the same [notebook protocol](references/notebook.md). Resolve a shorthand such as “2番” only when the project and report are clear. Record the owner's words privately. Adoption, deferral, and rejection describe decisions. Record an outcome only when someone reports what happened after trying the change. Preserve adverse results. Add an anonymized lesson with its applicability when justified, so future reviews can retrieve it. Confirm the ID and the facts recorded.
