# 三元占有較正によるデザイン改善スキルの構築法

**Ternary Occupancy Calibration for Design-Improvement Agent Skills**

人間が Web サイト / GUI アプリに対して「もっといい感じにして」と依頼したとき、3 出力の人間評定が平均して **めちゃくちゃ良い** / **まあまあ良い** / **悪くない** に均等へ向かうスキルを、どう設計し、どう検証し、どう包装するか。

- 文書種別: 手法論文（method paper）。大規模被験者実験の結果報告ではない
- 対象読者: エージェントスキル作者、デザインエンジニア、評価設計者
- 実装先規約: `laststance/skills`（`SKILL.md` + 遅延ロード、エージェント非依存が既定）
- 用語の正本: 品質帯の公式名は日本語ラベル。英語グロスは補助

---

## 要旨

「もっといい感じにして」は、成功条件が数値化されていない依頼である。現行のコーディングエージェントは、この依頼を **単一の最良改善** へ畳み込みやすい。その結果、出力は次の二極にモード崩壊する。

1. **安全な中央値** — 既存トークンを少し整えただけの「まあまあ良い」
2. **偽の頂点** — Inter / 大きな角丸 / 紫グラデ / 汎用 shadcn 美に寄った「めちゃくちゃ良い」風

どちらも、依頼者の選択を狭める。本稿の主張は、品質を最大化することではない。**1 回の依頼に対して 3 つの実装済み改善を束（bundle）として出し、人間が各出力を独立に評定したとき、三つの日本語品質帯の出現頻度が平均して均等に近づくスキル** を構築する手順を与えることである。

三帯はいずれも「壊れていない」より上に置く。

| 公式ラベル | 記号 | 英語グロス | 依頼者が口にする反応の目安 |
|---|---|---|---|
| めちゃくちゃ良い | \(G^\star\) | delight | 「これ、人に見せたい」 |
| まあまあ良い | \(G\) | solid | 「ちゃんとしたデザイナーが通った」 |
| 悪くない | \(G^-\) | acceptable | 「これなら出していい / 無難に良くなった」 |

生成時、スキルは各出力に **意図バンド** \(I\) を一つ割り当てる（1 束で三帯を一つずつ）。検証が測るのは \(I\) そのものではなく、評定者が \(I\) を知らずに付ける **受領評定** \(H\) の分布である。\(I=H\) の完全一致は診断用の混同行列であり、採択条件ではない。ラベルを出力に印刷してから同じラベルを付けさせる手続は、均等をトートロジーにするので禁止する。

採択は改訂用 **4 ゲート** と holdout **3 ゲート** である（定義は §4.2）。A/B は均等の二指標。不全率は両方、位置差は改訂用だけが名乗りの必須条件である。

- **周辺一様性 (A)**: 改訂用 30 は \(\max_k|\hat{p}_k-1/3|\le\varepsilon=0.08\) かつブートストラップ 95%点 \(\le\gamma=0.15\)。holdout は各帯件数 \(|n_k-N_c|\le 2\)（\(\varepsilon\) は使わない）
- **バンドル置換率 (B)**: 改訂用 30 は \(\hat{\tau}\ge\tau_0=0.45\) かつブートストラップ 2.5%点 \(>2/9\)。holdout は置換件数 \(\ge 5\)（\(\tau_0\) は使わない）
- **不全率**: \(\hat{q}_{\mathrm{inc}}\le 0.10\)
- **位置差**: 個人評定の位置別 \(P(H=k)\) を三帯それぞれについて取り、幅の最大 \(\le 0.15\)。**改訂用 30 だけ**（\(N<30\) の holdout には課さない）

holdout 10 に改訂用と同じブート条項を課すと、\(\hat{\tau}=0.50\) でも 2.5%点が \(2/9\) を超えず、実質 \(\tau_0\) が約 0.60 に上がる。holdout の A は **件数窓 \(|n_k-N_c|\le 2\)**、B は **置換件数 \(\ge 5\)** である。\(\varepsilon=0.08\) と \(\tau_0=0.45\) は改訂用 30 専用。位置差も holdout には課さない（\(N_c\approx 9\) で幅 0.15 はノイズで落ちる）。

本稿は実験結果を報告しない。代わりに、スキル作者が実装し、評定し、棄却または採択できる手続きを固定する。

## 1. 導入

### 1.1 依頼クラス \(R\)

本稿が扱う依頼は、次をすべて満たす発話およびその言い換えである。

- 対象が **既に存在する** Web サイトまたは、ブラウザで実行時証拠が取れる GUI の、**名前付き 1 画面** である。ネイティブ専用は \(R\) の外
- その画面は URL と到達状態（ログイン、クエリ、開いたパネル、凍結したビューポートと color-scheme）で指せる
- 対象画面のソースが、エージェントの **git 作業樹**（または同等の clone）として開かれている
- 依頼者が求める変化は **見た目と操作感の質** である（新機能追加は主目的ではない）
- 成功条件は「もっといい感じ」「なんかダサい」「polish して」など、**評定可能だが数値化されていない**

このクラスを \(R\) と書く。1 回の \(R\) 実行は **1 画面 → 1 束** である。サイト全体への依頼は、画面ごとの TOC 実行を並べる。サイト全体を 1 束で再スタイリングすることは対象外である。\(R\) はヒューリスティック評価（Nielsen & Molich, 1990）が扱う「使えるか」とも、visual regression が扱う「前と違うか」とも、機能 QA が扱う「動くか」とも一致しない。\(R\) が問うのは、**いまのその画面を、壊さずに、人がより良く感じるか** である。

### 1.2 単一出力最大化の失敗

\(R\) に対して「最善の 1 案」を出すスキルは、次の理由で依頼者の役に立ちにくい。

- **嗜好はスカラーではない。** 同じ画面でも、保守的な出荷と、記憶に残る再設計では、採用条件が違う。
- **典型性バイアス。** 選好学習を経たモデルは、よくある「良い UI」へ収束する（Zhang et al., 2025, Verbalized Sampling）。デザインではそれが Inter・大きな radius・紫アクセント・汎用カードグリッドとして現れる。
- **中央収束。** 細かい絶対評定は中央に寄りやすい。本稿は帯を 3 値に固定する。これは較正手続の選択であり、粗い尺度が常に強いという主張ではない。
- **選択の欠如。** 依頼者は「良くして」と言いながら、実際にはリスク許容度を後から決める。1 案は、その決定を先取りして潰す。

束サイズ 3 は、三帯を一つずつ置く最小整数である。4 以上の束は本稿の対象外とする（較正が別問題になる）。

### 1.3 本稿が答える問い

> スキル \(S\) をどう書けば、\(R\) に対する 3 出力束 \(Y = \{y_1, y_2, y_3\}\) を、人間評定 \(H(y) \in \{G^\star, G, G^-\}\) が **平均して均等** に付ける状態へ、作者が寄せられるか。

「平均して均等」の操作的定義は §4.2 に置く。ここでの要点は、均等を **生成時のスローガン** にせず、**独立評定の事後分布** として測ることである。

### 1.4 貢献

1. \(R\) に対する三帯の操作的定義と、帯に入らない **不合格** の分離（§2）
2. 意図バンドと受領評定を分離した **三元占有較正（TOC）** の手続（§3–§4）
3. 介入強度 4 軸による、帯漏れを減らす生成契約（§3.3）
4. 4 ゲート（A/B/不全率/位置差）。改訂用 30 はブートと位置差付き。holdout 10 は A が件数窓 \(|n_k-N_c|\le 2\)、B は置換件数 \(\ge 5\)、不全率（位置差なし）（§4）
5. `laststance/skills` へ落とす包装手順（§5）

## 2. 品質帯の操作的定義

評定はラベルの語感に頼らない。各帯は **観察可能な反応** と **禁止事項** で定義する。英語グロスは非日本語評定者用の補助であり、公式名は置き換えない。

### 2.1 不合格（帯の外）

次の番号付きリストのいずれかがあれば、その出力は三帯のどれにも入れない。記号は \(F\)。生成フロア、§2.6、金標準、倫理は **このリストだけ** を \(F\) と呼ぶ。

1. 機能退行（以前できた操作ができない、誤った状態表示）
2. 指定レンダー欠陥。正本は次の 6 種の判定文だけである。visual-lint コードは探索補助であり、第二の \(F\) リストではない。画素が判定文に当たれば \(F\)。表に無いコードでも当たれば \(F\)。6 種外（接触だけ、孤児語、化粧品、hover の lift だけ、凍結ビューポート外の未到達スクロール内容）は条項 2 にしない。

   | 種 | 判定文 | よく当たる visual-lint コード |
   |---|---|---|
   | 折り返し | 1 行であるべき語が 2 行以上 | A1, A7 |
   | 欠け | 必要なグリフまたは面が潰れて無い | D5、A6 の tofu / missing icon / mojibake |
   | 重なり | 2 要素の画素が重なる。接触だけは重なりではない | A5 |
   | 切れ | 凍結ビューポート内で、到達可能な内容が枠で切断されている。ビューポート外の未到達スクロールは切れではない | A2, A3, B1, B3 |
   | 読めないコントラスト | after 単体で文字または必須 UI が地に沈む。before より悪化しただけの退行は条項 3 であり、条項 2 に数えない | E1, E2 |
   | ターゲット過小 | 操作可能なコントロールの当たり領域が明らかに小さい | D3 |
3. アクセシビリティ退行（フォーカス消失、コントラスト低下、動きの止め方の喪失、名前付けの喪失）
4. 第二のスタイリング系統の導入
5. 既存トークンを無視したワンオフ色・型・影。対象は **名前の無い** hex、名前の無い連続量、反復 1 点だけのワンオフ影/型だけである。名前付きの新色相・新トークン・新役割で反復 2 点以上は条項 5 の外であり、強制問の決断にする。局所にも色の 1 段階にも落とさない
6. ブランド破壊（プロダクトがそう見えてはいけない見た目への勝手な転向）
7. ダークパターン、または注意の搾取
8. テンプレ美（偽の頂点: 紫グラデ、ガラスカードの量産、意味のない blob、Inter への無断置換など、よくある AI slop を「テーゼ」と偽る）
9. 散らかった改変: 決断 0 かつ顔局所数（クラフト変更だけ。§2.1-2 の修復は数えない）が 2 以上かつ統一原則なし
10. 決断次元数が 2 以上。同一顔次元の複数規則はテーゼ 1
11. 観察可能な改善が 0。判定は視覚だけである。before と after を孤立提示し、3 秒で画素上の違いを 1 つも言えない。git diff は使わない。見えない属性だけの after は 11。見えるコピー変更やフォーカスリング追加は 11 ではない

**統一原則** の正本は §2.4 である。ここでの言い換えは使わない。

\(F\) は「悪くない」ではない。**悪くないは、壊れていない上での控えめな改善** である。較正セットに \(F\) を混ぜ、評定者が \(G^-\) と \(F\) を混同しないことを先に確認する。

**顔** の次元は次の 7 つに固定する。§2.2–§3.3 もこの集合だけを使う。ヒーローやナビは骨格レイアウトの例であり、別次元ではない。

キーカラー / 骨格レイアウト / タイプ骨格 / 反復モチーフ / リズム / モーション原則 / 素材

### 2.2 \(G^-\) 悪くない（acceptable）

**何をする帯か。** 欠陥と、誰が見ても雑なクラフトだけを上げる。新しい美的テーゼは出さない。既存の視覚言語の内側に留まる。

**観察可能な印**（H の必要十分条件は §2.6。ここは言い換えであり、点数だけで \(G\) に上げない）。

- 木の \(G^-\) 葉: 決断 0、統一原則なし、顔局所（クラフト）0 または 1
- 変更は局所に見える。クラフトは色の 1 段階 **または** 余白 1–2 点の一方だけ（1 次元）。欠け修復と状態色は加えてよい
- 色の 1 段階は統一原則表に無い。何点でも統一原則にはならない
- 依頼者が before/after を 3 秒見比べて、「前よりマシ。説明は要らない」と言える

**生成契約上の禁止**（H の木には出さない。破った結果が §2.1 に当たれば木が \(F\) にする）: 新しいフォントファミリー、新しいキーカラー、レイアウト原則の変更、装飾モーションの追加。

### 2.3 \(G\) まあまあ良い（solid）

**何をする帯か。** 既知のクラフトを、画面の支配的な表面に対して漏れなく適用する。新しい「見た目の主張」は持たないが、プロの手が通った密度になる。

**観察可能な印**（H の \(G\) 入口は木ステップ 5 だけ。列挙は生成目標であり、全部必須ではない）。

- 決断 0 かつ、名前付き統一原則が支配的表面に 3 点以上（他原則は任意）
- 依頼者が「特別ではないが、出荷して恥ずかしくない」と言える
- 変更は局所パッチの集合ではなく、**同一原則の横断適用** に見える

**生成契約上の禁止**（H は木だけ）: 未所持モチーフの導入（ガラス、ネオン、ブロークングリッド、新しいイラスト系統）。「一発で覚える画面」を狙うこと。

### 2.4 \(G^\star\) めちゃくちゃ良い（delight）

**何をする帯か。** 制約の内側で、**ちょうど一つのテーゼ** を通す。

各顔次元は before と比較して次の **ちょうど 1 水準** を取る。水準は 3 つだけである。一点改変は使わない。

| 水準 | 判定文 |
|---|---|
| 不変 | その次元に見える変化が無い |
| 局所 | 見える変化があり、強制問はいいえ（既存規則の横断を含む） |
| 決断 | 強制問がはい |

**強制問**（各次元について、この文だけを使う）: 「この次元で、before に無かった新しい原則または新しいトークン系統を、顔 7 語から 1 つで言え、その反復箇所を 2 点以上指せるか。」はい → 決断。いいえ、かつその次元に見える変化がある → 局所。変化が無い → 不変。既存規則の横断（タイプスケールを揃える、余白リズムを通す）は新しい原則ではない。**色の 1 段階** は、プロジェクトの既存スケール（Tailwind 番号、デザイントークンの隣ストップ）で、同じ色役割を隣へ 1 つだけ動かすことである。凍結表の別リストは要らない。スケールが無いときは、同じ色相のまま明度を一段だけ変える。色相変更、役割の新設、パレット外 hex は 1 段階ではない。1 段階は反復 2 点以上でも決断ではない。色役割の変化は顔次元 **キーカラー** に載せる。

**テーゼ数** は決断水準の次元数である。同一顔次元に規則がいくつあっても 1。条項 10 もこの数え方だけを使う。**統一原則** は、決断数 0 かつ、次表の名前のうち **少なくとも 1 つ** が支配的表面に 3 点以上あることである（複数可。§2.3 の総動員も \(G\)）。局所の変化箇所は 3 点に数える。どれも 3 点未満なら統一原則ではない。

| 統一原則の規則名 | 載せる場所 |
|---|---|
| タイプスケール | 顔: タイプ骨格 |
| 余白リズム | 顔: リズム |
| 同心半径 | 顔: 素材 |
| アイコンウェイト | 顔: 反復モチーフ |
| 状態揃え | 非顔（顔局所数に足さない） |
| 階層 | 顔: 骨格レイアウト |
| 影/境界 | 顔: 素材（幅/スタイル/影。境界色はキーカラー） |

**点** は画面上で指せるコンポーネントインスタンス 1 つである（カード、行、見出し、本文、ボタン、入力）。空状態はブロックに畳まない。内部の見出し・本文・操作を各 1 点に数える。CSS 変数を 1 箇所変えて N 枚に効いても、見えるインスタンス数を数える。グリッド 12 枚の余白揃えは 12 点。領域全体を 1 点に畳まない。較正セットには支配的表面の点が 3 未満の画面を入れない。実行時に 3 未満でも \(I=G\) は禁止しない。

**支配的表面** は **画面 1 つにつき 1 つ** である。較正では生成より前に、before に対して CSS セレクタ 1 つか矩形 1 つを凍結表へ書く。3 after と G 契約と評定は、この同じ指し示しだけを使う。after 列は作らない。ナビ・クロームは含めない。開いたモーダルがあるときはその本文ノードを書く。実行時は、開いたダイアログ本文、なければ `main`、なければ親が選んだ本文ブロック 1 つを帯契約に書く。

同一画面での余白リズム三帯（金標準の境界でもこれを使う）:

- \(G^-\): 余白揃え 1–2 点。リズムは局所。決断 0。統一原則なし
- \(G\): 余白リズムを支配的表面に 3 点以上。リズムは局所。決断 0。統一原則 = 余白リズム
- \(G^\star\): 余白リズムを製品の武器にする新しい原則。リズムは決断

ステップ 3 の「顔局所数」は、水準が局所である顔次元のうち、**クラフト変更** だけを数える。§2.1-2 の欠陥修復は、判定文を偽にする **最小変更** に限る。それは顔局所数にも統一原則の 3 点にも数えない（修復後は不変でもよい）。最小を超える同一規則の反復（タイプスケールで折り返しを消したうえで 3 点以上揃える等）はクラフトであり、顔局所と 3 点に数える。修復だけの after はステップ 6 の \(G^-\) である。§2.1-9 はクラフト変更の散らかりだけに適用する。非顔の修正（状態色など）は顔局所数に足さない。状態揃えの 3 点には数える。

**観察可能な印。**

- 3 秒で「何を決めた画面か」が言える（例: 骨格を新聞的階層に再編成した、キーカラー一点だけが動く、余白リズムを製品の武器にした）
- その決断が、画面の複数箇所に反復され、一貫している
- 依頼者が「好き嫌いは分かれるが、見せる価値がある」と言える
- 既存トークン・アクセシビリティ・ブランドのハードフロアは守っている

**禁止。**

- テンプレ美の移植（よくある AI slop: 紫グラデ、ガラスカードの量産、意味のない blob、Inter への無断置換）
- テーゼが 2 つ以上ある（§2.1-10）
- §2.1 の 1–7 を「美しさ」のために割ること

### 2.5 帯は順序を持つが、採用価値は順序ではない

クラフト上の野心は \(G^\star > G > G^-\) である。しかし **出荷価値は依頼者のリスク許容度に依存する**。金曜日のホットフィックスでは \(G^-\) が正しく、ポートフォリオ提出では \(G^\star\) が正しい。均等占有は、スキルが依頼者の代わりにリスクを先取りしないための設計である。

### 2.6 帯判定（全域関数）

評定者と較正セット作成は、同じ木を上から一度だけ辿る。本測定の \(H\) もこの木である。帯ごとの生成禁止は H に直接出さない。H の正本は木である。`judge-tree.md` はこの節の印刷であり、次をすべて載せる。§2.1 の番号付き条項（条項 2 表を含む）と顔 7 語、§2.4 の水準・強制問・テーゼ数＝決断次元数・統一原則の定義文（決断 0 かつ名前付き規則が支配的表面に 3 点以上）・統一原則表・点・支配的表面（評定者は凍結された指し示しを使い、測り直さない）・色の 1 段階例外・顔局所数のクラフト/修復規則・余白リズム三帯、§2.6 の木。これ以外を載せず、これ以外を配布しない。`anchors.md` は載せない。「テーゼが一つ」は決断次元数が **ちょうど 1**。同一顔次元の複数規則は 1。テンプレ美の徴候（§2.1-8 の例を含む。テーゼの有無を問わない）と改善 0（§2.1-11）はステップ 1 で \(F\) にする。どの入力も次の最初に当たった葉へ落ちる。

0. 7 次元を不変 / 局所 / 決断に分け、テーゼ数と統一原則を §2.4 で確定する
1. §2.1 の 1–8 または 11 のいずれか → \(F\)（条項 5 は名前の無い hex・連続量・1 点ワンオフだけ。名前付き新色相は決断側）
2. 決断次元数が 2 以上 → \(F\)（§2.1-10）
3. 決断 0 かつ顔局所数が 2 以上かつ統一原則なし → \(F\)（§2.1-9）
4. テーゼ数がちょうど 1 → \(G^\star\)
5. 決断 0 かつ統一原則がある → \(G\)
6. それ以外 → \(G^-\)

ステップ 4 が \(G^\star\) の唯一の入口。ステップ 5 が \(G\) の唯一の入口。ステップ 6 は決断 0・統一原則なし・顔局所数 0 または 1 で、11 でもない葉である（非顔だけの局所修正を含む）。

## 3. 三元占有較正（TOC）

### 3.1 対象と非対象

**対象。** 依頼クラス \(R\) に応じる **生成スキル** の書き方と、その較正。既存画面を読み、3 つの実装済み改善を出す。

**非対象。**

- 欠陥検出だけの監査（`/visual-lint`, `/ux-gap-detector`）。それらは TOC の入力になり得るが、帯を占有しない
- ゼロからのデザインシステム策定（`/design-consultation` 系）
- 「常に最高にしろ」という単一出力スキル。TOC はそれと目的が違う
- 人間の趣味そのものの普遍化。帯は較正可能な契約であり、美の本質定義ではない
- ソースリポジトリが無く、URL のオーバーレイだけを出す依頼

### 3.2 意図と受領の分離

各出力 \(y_i\) は生成時にちょうど一つの **意図バンド** \(I(y_i) \in \{G^\star, G, G^-\}\) を持つ。1 束は意図の上では必ず三帯を一つずつ含む。

\[
\{I(y_1), I(y_2), I(y_3)\} = \{G^\star, G, G^-\}
\]

評定者は \(I\) を見ない。同一の帯評定者 3 人が、各 \(y\) を **before + その after だけ** で順に見る（横並び同時提示は禁止。同一評定者が 3 after を順に見ることは許す）。多数決後の \(H(y) \in \{G^\star, G, G^-, F, U\}\) を付ける。生成不全は評定しない。評定不全（多数決に \(F\) または \(U\)）は指標 A/B から除外する。どちらも §4.4 の \(\hat{q}_{\mathrm{inc}}\) に数える。

成功は \(I = H\) の完全一致を要求しない。成功は §4.2 の改訂用 4 ゲートと holdout 3 ゲートである。\(I \neq H\) の混同行列は診断表である。

### 3.3 介入強度の 4 軸

帯を文章で宣言するだけでは、モデルは三出力を言い換えて同じ画面を出す。帯の差は **変更してよい範囲の契約** として書く。軸は 4 つ。各軸は順序尺度であり、数値の絶対値に意味はない。

| 軸 | \(G^-\) | \(G\) | \(G^\star\) |
|---|---|---|---|
| **範囲 (Scope)** | 局所。指摘面または欠陥面。クラフト局所は高々 1 次元 | 支配的表面で統一原則を 3 点以上（他原則は任意） | 決断はちょうど 1 次元。他次元は局所または不変 |
| **リスク (Risk)** | 既存視覚言語の内側 | 既存言語の密度を上げる。新モチーフは禁止 | 既存制約の内側で、一つの新しい決断を許す |
| **可逆 (Reversibility)** | 1 ファイル数行で戻せる | トークンまたは共通部品への横断だが、原則は増えない | 原則が一つ増える。戻すと顔が消える |
| **驚き (Surprise)** | 説明不要。差分は「修正」に見える | 説明は「原則の適用」で足りる | 説明は「何を決めたか」になる。テンプレ美は失格 |

スキル本文は、帯ごとにこの 4 軸を **やってよいこと** として書く。禁止の列挙だけにすると、モデルは禁止概念を活性化して漏れる（指示文書における否定の失敗）。

### 3.4 生成手続（作者がスキルに書く手順）

エージェントが \(R\) を受けたとき、手順 0–6 をこの順で行う。自己検査が \(F\) の案だけを捨て、同じ帯を取り直す。帯あたり試行は最大 3 回（初回 + 再生成 2）。\(H \neq I\) と「三出力が同じ顔」は再生成条件にしない。

**同じ顔。** 3 after それぞれについて、§2.4 と同じ 3 水準ベクトル（各顔次元が 不変 / 局所 / 決断）をステップ 0 と同一関数で書く。3 ベクトルが一致するとき同じ顔である。ゼロベクトルどうしも同じ顔。上の余白リズム三帯は \(G^\star\) だけが決断なので同じ顔ではない。

**実行時**（依頼者が 1 画面を投げた日常利用）: 3 回とも \(F\) の帯がある束、または三出力が同じ顔の束は **未完了** である。2 出力を TOC 束として渡してはならない。同じ顔の 3 after は見せてよいが、TOC 完了とは言わない。支配的表面の点が 3 未満でも意図三帯は出す。\(I=G\) は存在する点のすべてに既存規則を通す。\(H\) が \(G^-\) でも再生成しない。そのような画面は較正セットに入れない。較正の \(N\) や帯評定者は実行時に出さない。

**較正時**（§4）: 3 回とも \(F\) の帯がある束は **生成不全** として閉じ、評定に回さない。画面は凍結集合に残す。

**手順 0 — 証拠。** 対象画面の実行中 UI を見る。コードだけ、記憶だけで帯を割り当てない。スタイリング系統（Tailwind / CSS / CSS-in-JS）を特定し、第二系統を足さない。

**手順 1 — フロア。** 用語「フロア」は §2.1 の **1, 3–7** だけを指す。条項 2（指定レンダー欠陥）は生成チェックに残すが、フロア検査の担当外である。フロア 1, 3–7 と条項 2 を 3 つの worktree 契約へ同じ文面で写す。共有 base commit に先に入れて 3 分岐してはならない。\(G^-\) の仕事は「その一覧 + 局所クラフト」、\(G\) / \(G^\star\) は「同じ一覧 + 帯契約」。どの帯もフロアを免除されない。

**手順 2 — 現状の顔。** 画面がいま何で覚えられているかを、§2.1 の 7 次元で一文に書く。この文が、\(G^-\) が壊してはいけないもの、\(G^\star\) がちょうど一点だけ置き換えてよいものである。

**手順 3 — 帯契約の固定。** 静的ファイル `references/band-*.md` は 4 軸のテンプレである。オーケストレータ（親エージェント）が、この画面の語彙へ翻訳した契約を **各 worktree 局所** に 1 ファイルずつ書く。例: 「\(G^-\) はヒーロー内の Card 1 枚の半径だけ（共通トークンは触らない）」「\(G\) は余白リズムを支配的表面に 3 点以上通す。新原則は足さない」「\(G^\star\) は骨格を密度優先に再編成する。キーカラーは触らない」。生成単位は、自分の worktree にある契約 1 ファイルだけを読む。静的テンプレ 3 つを同じコンテキストに読み込んではならない。

**手順 4 — 隔離生成。** 3 帯は **別コンテキスト・別 git worktree（または別 clone）** で実装する。同一会話で 3 バージョンを出すことを禁止する。実装は `Task` 3 本、または帯ごとに新しい会話 3 回。`Task` を使うスキルは `# Title` の直後に対応表を置く。完了物は 3 worktree が残っていること。単一作業樹での checkout / revert 循環は生成でも評定でも「3 実装」に数えない。評定は 4 インスタンス（before + 3 after）を別ポートで起動できることを原則とする（例: `:3000`–`:3003`）。ホストが同時 4 ポートを持てないときだけ、**残してある 3 worktree を順に起動** して孤立提示する。同一ツリーを持ち替えることは、この例外にも入らない。

**手順 5 — 自己検査。** オーケストレータだけが、ゲート通過後に凍結した `references/judge-tree.md` を読む。生成単位は読まない。親は after を 1 つずつ、\(I\) を隠して木を通す。**葉が \(F\) のときだけ** 同じ帯を再生成する（帯あたり最大 3 試行）。\(H \neq I\) は再生成しない。三出力が同じ顔なら記録する。再生成はしない。実行時は未完了。較正では評定に回す（生成不全ではない）。較正で帯が 3 回 \(F\) なら生成不全であり、評定に回さない。

**手順 6 — 提示。** 依頼者には各 after を **before + その after だけ** で順に見せる。横並び 3 枚は禁止。意図ラベルは、較正が §4.2 と holdout を満たすまで出さない。動きを契約した帯は、生成後・評定前に休止 1 枚と動作が分かる連続フレームを凍結する。強制問はそのフレーム上で反復 2 点以上を指して答える。帯評定者 3 人は実行時には出さない（§4.1）。

### 3.5 スキル本文に置くもの、開示するもの

エージェント向け文書の負荷は二種類ある。常時載る **コンテキスト負荷** と、人間がどれを開くかの **認知負荷** である（writing-for-agents の整理）。TOC スキルでは次に固定する。

**`SKILL.md` に残す（毎実行）。**

- 依頼クラス \(R\) の判定（1 画面 1 束）と、対象外
- 不合格 \(F\) へのポインタ（定義の正本は `judge-tree.md`。生成単位は読まない）
- 手順 0–6 の **実行時** 完了条件（worktree、隔離、孤立提示、同じ顔なら未完了）。手順本文は `workflows/generate-bundle.md` にだけ置き、`SKILL.md` へ重複させない
- 「帯契約ファイルは 1 実行単位につき 1 つだけ読む」
- 3 出力を意図三帯で閉じること。実行時に帯が 3 回 \(F\)、または同じ顔なら未完了
- 較正の \(N\)・評定者・ブートストラップは `SKILL.md` に置かない（`references/calibration.md`）

**遅延ロード（生成単位は自分の帯ファイルだけ）。**

- `references/band-g-minus.md` / `band-g.md` / `band-g-star.md`（各帯の 4 軸契約。三帯表の全文を `SKILL.md` に置かない）
- 生成単位が読んでよいのは、自分の worktree にある帯契約 1 ファイルだけである
- `anchors.md` / `confusion-repair.md` / `calibration.md` / `toc_gate.py` / `toc_alpha.py` は作者・凍結者専用。評定者用は `judge-tree.md` だけ。生成単位は読まない

`description` は第三人称で、**何をするか** と **いつ使うか** を両方書く。トリガー語に「もっといい感じ」「polish」「feel better」「ダサい」を含める。

### 3.6 既存 laststance スキルとの位置

| スキル | 問うこと | TOC との関係 |
|---|---|---|
| `/visual-lint` | レンダーは壊れているか | 条項 2 の入力。フロア検査ではない。TOC は直す |
| `/ux-gap-detector` | SaaS 内面の UX ギャップは何か | 入力の候補。帯は持たない |
| `/product-inspiration` | 上位アプリは何をしているか | \(G^\star\) のテーゼ探索に使える。移植そのものは偽の頂点 |
| make-interfaces-feel-better（クラフト原則） | 細節は正しいか | 主に \(G\) の中身。原則の総動員は \(G^\star\) ではない |
| 単一出力の design-review 系 | 美的に良いか、そして直せ | 最大化スキル。TOC とは目的が違う |

TOC スキルはこれらを再実装しない。フロアと原則は参照し、**3 帯の占有** だけを自分の仕事にする。

## 4. 検証手続

### 4.1 評定プロトコル

**評定単位。** 1 試行 = 名前付き 1 画面（URL + 到達状態）+ before 1 + after 3。画面の繰り返しは禁止する（同じ URL+状態を 2 束目に使わない）。

**孤立提示。** 同一の帯評定者 3 人が、各 after を **before + その after だけ** で順に見る。横並び 3 枚は禁止。独立な無作為順列は禁止する。提示順は試行内ラテン方格に固定する。after の身元は意図帯 \(Y^-,Y,Y^\star\)（生成時に 1 対 1）。基本方格 \(\mathrm{BASE}[r] = [(Y^-,Y,Y^\star),\ (Y,Y^\star,Y^-),\ (Y^\star,Y^-,Y)][r]\)。試行番号 \(t\) は凍結表の番号である（改訂用 \(0{\ldots}29\)、当初 holdout \(30{\ldots}39\)、予備 \(40{\ldots}49\)）。評定者 \(r\) の位置 \(p\) に出す after は \(\mathrm{BASE}[r][(p+t)\bmod 3]\)（左シフト）。腕ごとの 0 始まりは使わない。右シフトも無作為も使わない。媒体は変更に合わせる。モーションを契約した after の **見た目評定** は、較正では凍結した保存フレームだけである（再生のライブ操作は較正に使わない）。条項 1,3–7 のフロア検査・金標準 (c)・帯評定の見落とし捕捉は、次の操作手順を **1 周だけ** 行ってよい。Tab でフォーカス可能を一巡する。主操作を各 1 回起動する。動きの停止コントロールがあれば 1 回試す。自由探索は禁止する。

**独立評定。** 個人セルは木の葉 \(H \in \{G^\star, G, G^-, F\}\) だけである。空白・判断不能・破損票は個人 \(U\) として書かず、その試行を評定不全にして `completed` に入れない。\(U\) は 3 票の多数決に多数が無いときの結果に限る。三帯を一つずつ割り当てる強制割当は使わない。

**役割の分離。**

- **生成者** はスキルを走らせる人またはエージェントである。評定しない。\(I\)、プロンプト、生成ログを評定者に渡さない
- **フロア検査** はプロダクトにアクセスできる 1 名。帯評定も生成も兼ねない。本測定で §2.1 の **1, 3, 4, 5, 6, 7** を付ける。ここが \(F\) ならその出力は \(F\) で確定する。金標準 12 の `floor_137` 欄と、フロア検査が条項 1,3–7 だけ見て付けた F/非F が不一致 0 でなければならない。外れならフロア検査を差し替える。見える側の判定は凍結欄であり、検査者が「見えない」と返して集合を空にしてはならない
- **帯評定者** は 3 人。うち外部 \(\ge 1\)。既定は内部 2 + 外部 1。外部を増やして内部を減らしてよい（合計 3）。3 人とも同じ 1 枚シートを持つ。本測定では、フロア非 \(F\) の出力に対し木を **ステップ 1 から** 付ける（2, 8, 9, 10 と、フロアの見落とし）。金標準ではフロア検査を出さず、3 者がシートを持ってステップ 1 から付ける

§2.1 の担当（「測定可能な条項」という語は使わない）:

| 番号 | 本測定 | 金標準 |
|---|---|---|
| 1, 3–7 | フロア検査が先。見落としは帯評定のステップ 1 | 帯評定 3 者だけ |
| 2, 8–11 | 帯評定 3 者だけ | 帯評定 3 者だけ |

指標 A/B のラベルは帯評定 3 者の **多数決** である。多数が無い出力は \(U\)。その試行は不全。主評定者への事後切替はしない。

**ブラインド。** 帯評定者は \(I\)、生成プロンプト、生成ログ、作者予想を見ない。生成者と帯評定者は交わらない。本測定の 3 者は、次の金標準ゲートを通った同一 3 者である。

**較正セット。** 生成より前に行う。金標準 12 件は **before + after**（到達状態付き）。提示は本測定と同じ孤立 1 組ずつ。提示順は凍結表に固定し、帯ラベルは隠す。横並びも帯ごとの塊提示も禁止。凍結 50（改訂用 30 + holdout 10 + 予備 10）の URL+状態と **互いに素** にする。評定者配布物は `judge-tree.md` と、各画面の凍結した支配的表面の指し示しだけである。`anchors.md` は凍結者 / 作者専用。帯 9 件（各帯 3）のうち、余白リズムが決断になる境界と統一原則になる境界を 1 件ずつ、色の 1 段階が局所クラフトになる境界を 1 件含める。\(F\) 3 件は (a) \(\{8,9,10\}\) から 1 件、(b) 条項 2 のうちコントラスト以外の 5 種から 1 件、(c) \(\{1,3{-}7\}\) から 1 件。各 12 件に凍結欄 `floor_137`（条項 1,3–7 が見えるか）を全員一致で付ける。(c) だけ `yes`、他 11 は `no`。両方当たるコントラスト画素は条項 3 だけに数える。ラベル凍結者は生成者でも帯評定者でもない 2 名以上。凍結は **全員一致** に限る。1 件でも不一致ならその件を差し替えるか、§4.1 の注釈手続に進む。帯評定者は凍結ラベルを見ない。ゲート失敗でラベルを書き換えて通してはならない。木の注釈を足したら次をこの順で行う。(1) 同じ金標準 12 を同一 3 者が再評定し、3 ゲートを取り直す。(2) 改訂用 30 の生成物と評定は捨て、同じ凍結 URL で再生成する。holdout が未評定なら再生成せず、URL と予備は保持し、生成・評定は手順 7 までしない。(3) holdout の評定が一度でも済んでいたら TOC 名乗りは無効であり、失敗 URL は捨て、新しい holdout 10 と新しい予備 10 を評定より前に凍結する。改訂用 URL の \(t=0{\ldots}29\) は保持し、新 holdout / 予備だけ \(t=30{\ldots}39\) と \(t=40{\ldots}49\) を振り直す。改訂用は再生成した束で 4 ゲートを取り直してから手順 7 を行う。それでもゲートが落ちるなら新しい 12 件を凍結からやり直す。

\(\alpha\) は `scripts/toc_alpha.py`（付録 D）だけを使う。符号化 \(G^-=0,\ G=1,\ G^\star=2\)。金標準帯への \(F\) はそのセルだけ `nan`。`krippendorff==0.8.2` で `krippendorff.alpha(reliability_data=data, level_of_measurement="ordinal", value_domain=[0, 1, 2])`。0.8.2 は ordinal と `value_domain` をこの符号で受け付ける。文字列ラベルをそのまま渡さない。帯評定の 1 枚シートは `judge-tree.md` の印刷である。

### 4.2 「平均して均等」の二指標

指標 A/B は母集団推論ではなく、**事前固定した 30 画面に対するスキル成果物の採択ゲート** である。見たあとで標本を足さない。適合度検定の非棄却、独立な Wilson 区間、独立な二項検定は使わない（束内の負の依存と、画面クラスタを無視するため）。

**凍結条件** は次の組である。画面 50 に \(t=0,\ldots,49\) を一意に振り、列で改訂用 30 / 当初 holdout 10 / 予備 10 を印す。予備 10 は **最初の holdout 評定より前** に凍結する（既定は改訂用 30 と同時）。提示順と `toc_gate.py` の `t` はこの番号だけを使う（腕ごとの 0 始まりは禁止）。モデル ID、デコード、道具、スキルハッシュ、ビューポート幅×高さ（既定 `1440×900`）、color-scheme（`light` または `dark` を 1 つ。両方測るなら URL+状態+scheme で別行）、評定者 \(r=0,1,2\) の対応、役割ごとの名前付き色ストップ列、各 after の支配的表面、モーション after の休止+動作フレーム、条項 1,3–7 の操作は §4.1 の 1 周手順、定数 \(\varepsilon=0.08\), \(\gamma=0.15\), \(\tau_0=0.45\)（改訂用 30 専用）, holdout 置換件数下限 \(5\), \(\hat{q}_{\mathrm{inc}}\) 上限 \(0.10\), 位置差上限 \(0.15\), ブートストラップ回数 \(2000\), 種 `20250911`。金標準 12 と較正 50 の提示媒体は、このビューポートと scheme に固定する。データ閲覧後に定数を動かして TOC を名乗ってはならない。繰り返しは禁止。モデル ID が変わったら §4.5 を最初から取り直す。不採択のあと **スキル本文だけ** を直せる対象は改訂用 30 である。木を変えた場合は §4.1 の注釈手続に従う。当初 holdout も予備も、評定を見たあとで入れ替えない。同一 holdout 画面の評定は一度だけである。差し替えは名乗り 1 回につき最大 1 回（§4.5.8）。TOC を名乗るのは holdout が A（\(|n_k-N_c|\le 2\)）かつ B（置換件数 \(\ge 5\)）かつ \(\hat{q}_{\mathrm{inc}}\) を満たし、改訂用の位置差が既に通っているときに限る。改訂用 30 の通過だけでは名乗らない。

**凍結 50 画面の層。** 母集団の無作為標本ではない。層は排反である。名前付き画面の主仕事に、次を上から最初に当たった 1 つだけ付ける。(1) 空/エラー/オンボーディング: 主仕事が空状態、エラー画面、または初回オンボーディング本文。ログイン・サインアップ・パスワードリセットはここではない (2) 密な設定/データ: 主仕事が設定、権限、テーブル、ログ、スキーマなどの高密度操作（サインイン済みでもここ） (3) 認証済みアプリ内面: サインイン後のアプリ本体で (1)(2) ではない (4) マーケティング/ヒーロー: 未サインインの宣伝・ヒーローで (1) ではない (5) 残り: (1)–(4) のどれでもない。ログイン・サインアップ・パスワードリセットはここ。件数は改訂用と当初 holdout の **合計 40** で、各層を改訂:holdout = 3:1 で割る（密な設定/データ 8→6+2、認証済みアプリ内面 8→6+2、マーケティング/ヒーロー 4→3+1、空/エラー/オンボーディング 4→3+1、残り 16→12+4）。空/エラー/オンボーディングの **改訂用 3 枚** は空・エラー・オンボーディングを 1 枚ずつ含む。holdout 1 と予備 1 は三種のどれかでよい（差し替え後も改訂 3 枚が三種を保つ）。予備 10 は当初 holdout と同じ層件数（2+2+1+1+4）にする。差し替え後も改訂:holdout = 3:1 が保たれる。昇格した予備行の \(t\) は凍結時の番号（\(40{\ldots}49\)）のままである。提示に使った \(t\) を `toc_gate.py` へそのまま渡す。振り直してはならない。50 枚と金標準 12 は URL+状態がすべて互いに素。**プロダクト** は出荷されている名前付きアプリケーション 1 つである。マーケ起源ページとサインイン後 UI は、ブランド名とソースリポジトリを共有するなら同一プロダクト。同一 org の別アプリ、共有デザインシステムを借りた別アプリは別プロダクト。同一プロダクトから取る画面は 50 枚の中で最大 4、同一層では最大 2。ネイティブ専用、または実行時証拠が無い画面は入れない。50 枚はいずれも、既定ビューポートで支配的表面の点 \(\ge 3\)。空状態 1 ブロックやエラー 1 フィールドだけの画面は入れない。

試行を三つに分ける。**生成不全** は帯が 3 回 \(F\) で評定に回さなかった試行。**評定不全** は 3 出力を評定し、多数決に \(F\) または \(U\) がある試行。**完了試行** は評定済みで多数決がすべて \(\{G^\star, G, G^-\}\) の試行。A と B は完了試行だけを使う。完了試行数 \(N_c\)。改訂用で \(N_c < 27\)、holdout で \(N_c < 9\) なら A/B を採択せず、先に §4.4 を見る。生成不全と評定不全は交わらない。

**指標 A — 周辺一様性。**
完了試行の \(3N_c\) ラベルから帯割合 \(\hat{p}_k\) を取る。採択は次の両方である。

1. 改訂用 30: \(\max_k |\hat{p}_k - 1/3| \le \varepsilon=0.08\)。さらにブートストラップ 2000、Hyndman–Fan 型 7、種 `20250911` の 95 パーセンタイル \(\le\gamma=0.15\)
2. holdout 10: 件数窓。\(3N_c\) ラベルの各帯件数 \(n_k\) が \(|n_k-N_c|\le 2\)（\(N_c=9\) なら各帯 7–11、\(N_c=10\) なら 8–12）。\(\varepsilon=0.08\) は使わない。ブートストラップは課さない

**指標 B — バンドル置換率。**
完了試行のうち、3 評定の集合が \(\{G^\star, G, G^-\}\) と一致する件数を置換件数 \(n_\tau\)、割合を \(\hat{\tau}=n_\tau/N_c\) とする。独立一様なら \(2/9 \approx 0.222\)。採択は次である。

1. 改訂用 30: \(\hat{\tau} \ge \tau_0=0.45\)。さらにブートストラップ 2000 複製で \(\tau^\ast\) の型 7 の 2.5 パーセンタイル \(> 2/9\)
2. holdout 10: \(n_\tau \ge 5\)（\(N_c=9\) なら \(5/9\)、\(N_c=10\) なら \(5/10\)）。\(\tau_0=0.45\) は使わない。ブートストラップは課さない

位置差は B に入れない。第 4 ゲートであり、**改訂用 30 だけ** に課す。三帯 \(k\in\{G^\star,G,G^-\}\) それぞれについて、個人評定 `view[r][p]` が \(k\) である位置別割合の幅を取り、その最大 \(\le 0.15\)（付録 C）。多数決ラベルで位置差を取ってはならない。holdout 10 の位置差は記録してよいが、採択に使わない。

完了試行の個人評定 \(\alpha\) は **報告だけ**（ゲートに使わない）。行列は after 単位（Ym/Y/Ys）に戻した 3 行 × \(3N_c\) 列。\(F\)/\(U\) は `nan`。`toc_alpha.py` にこの行列を渡す。`view[r][p]` の位置順では計算しない。

改訂用の採択は **A かつ B かつ \(\hat{q}_{\mathrm{inc}}\) かつ位置差**。holdout の採択は **\(|n_k-N_c|\le 2\) かつ \(n_\tau\ge 5\) かつ \(\hat{q}_{\mathrm{inc}}\)**（位置差なし）。

ブートストラップの参照は付録 C（スキルでは `scripts/toc_gate.py`）である。完了試行を凍結画面番号の昇順に並べ、`numpy.random.Generator(numpy.random.PCG64(20250911))` で試行単位の復元抽出を 2000 回する。percentile は NumPy `method="linear"`（型 7）。作者が別 PRNG や別型で出した数値を採択に使ってはならない。

「平均して」は、毎回の完全占有を要求せず、改訂用と holdout のゲートを通すことを指す。

**失敗時の解釈。**

| 観測 | 診断 | 直す軸 |
|---|---|---|
| \(\hat{p}_{G}\) だけ大きい | 中央崩壊。三案が同じ密度 | 範囲と驚きを帯ごとに再契約。独立生成を強制 |
| \(\hat{p}_{G^\star}\) だけ大きい | 偽の頂点、または評定者が「違う＝良い」 | テンプレ美を手順 5 で \(F\) に落とす。金標準の件数は足すな。構成を変えるなら §4.1 の 12 再凍結 |
| \(\hat{p}_{G^-}\) だけ大きい | 野心不足、またはフロア修正だけで束を閉じている | \(G\) と \(G^\star\) の契約を画面語彙で具体化 |
| \(\hat{\tau}\) が 0.22 付近 | 帯が独立ノイズ。契約が文章だけ | 4 軸を帯別ファイルへ落とし、隔離生成を強制 |
| \(\hat{q}_{\mathrm{inc}}\) が大きい | フロア割れまたは評定不一致 | 手順 1 とフロア検査シートを強化。\(U\) が多いなら §2.6 を再較正 |

### 4.3 意図と受領の混同行列

行を \(I\)、列を \(H\) とした 3×3（\(F\) は別集計）。対角が薄いマスが、スキル改訂の対象である。典型パターン:

- \(I=G^\star, H=G\): テーゼが言えていない。驚き軸が空
- \(I=G^\star, H=F\): テンプレ美またはフロア割れ
- \(I=G, H=G^-\): 横断になっていない。範囲軸が局所のまま
- \(I=G^-, H=G\): 局所のつもりが統一原則（横断）まで行った
- \(I=G^-, H=G^\star\): 局所のつもりが決断 1 になった
- \(I=G^-, H=F\): 局所クラフトが 2 次元以上、またはフロア割れ

混同行列の改善は指標より先に見てよい。改訂用の採択は **A かつ B かつ \(\hat{q}_{\mathrm{inc}}\) かつ位置差**。holdout の採択は **\(|n_k-N_c|\le 2\) かつ \(n_\tau\ge 5\) かつ \(\hat{q}_{\mathrm{inc}}\)**（位置差なし）。TOC 名乗りは holdout 採択のあと、改訂用の位置差が既に通っているときに限る。

### 4.4 不全率

\[
\hat{q}_{\mathrm{inc}} = \frac{\text{生成不全} + \text{評定不全}}{N}
\]

採択の前提: \(\hat{q}_{\mathrm{inc}} \le 0.10\)。出力単位の \(F\) 率をこの記号で呼んではならない。

```
  references/judge-tree.md       # §2.1 + §2.4 + §2.6。評定者と手順5の親。生成単位は読まない
  references/anchors.md          # 金標準 12。凍結者/作者専用。評定者に渡さない
  references/confusion-repair.md # 混同行列 → 動かす軸（作者用）
  references/calibration.md      # §4（作者用。実行時エージェントは読まない）
  workflows/generate-bundle.md  # 手順 0–6 と worktree / ポート
  templates/bundle-report.md    # 1 after ずつの提示（較正前は帯名なし）
  scripts/toc_gate.py           # 付録 C。較正作者だけ
  scripts/toc_alpha.py          # 付録 D。α ゲートだけ
```

本文は第三人称の `description` を持ち、**Use when:** を含む。`SKILL.md` は 500 行未満。詳細は遅延ロード。ポインタは 1 段。

### 5.2 エージェント非依存

隔離生成は `Task`（またはホストのサブエージェント）か、新規会話 3 本である。対応表は隔離に `Task` / `TaskCreate` / ホストのサブエージェント primitive を使うときだけ `# Title` の直後に置く（`AGENTS.md`）。新規会話 3 本だけで隔離する実装は対応表を置かない。どちらの隔離も TOC である。primitive を使うのに対応表が無い隔離は、規約違反であり TOC でも無い。`AskUserQuestion` とプランモードは使わない（1 画面は依頼から既に特定されている）。

### 5.3 実行時の完了条件

スキルの成功は「3 ファイルを触った」ではない。次をすべて満たしたときだけ完了とする。

- 名前付き 1 画面の実行中 UI で before を確認した
- 3 after が別 worktree（または別 clone）として残っており、before とあわせて起動できる。同時 4 ポートを原則とし、不能時は残した worktree の順次起動だけを例外とする
- 実行時: \(F\) を 3 出力とも自己検査で通した。3 回 \(F\) の帯があれば未完了。三出力が同じ顔なら未完了。較正時、3 回 \(F\) は生成不全として評定に回さない。同じ顔は評定に回す
- 各生成単位は帯契約ファイルを 1 つだけ読んだ
- 意図三帯が揃っている
- 提示は before+after を 1 組ずつ（横並び 3 枚は禁止）
- 較正前なら帯名を出していない

### 5.4 README

`README.md` のインストール一覧、スキル表、使用例はアルファベット順。スキル数バッジを 1 増やす。依存は実際に必要なものだけ（ブラウザ検証があるならその実行系）。未較正のうちは、説明文に較正状態を書かない（未測定を成功に見せない）。

### 5.5 TOC をスキルに落とすときの最小本文

`SKILL.md` が必ず拘束する文は次である。言い換えて弱めてはならない。

1. \(R\) 以外では動かない。1 実行は名前付き 1 画面 → 1 束
2. 出力は 3、意図帯は三帯を一つずつ
3. \(F\) はどの帯にも入れない
4. 帯契約は帯別ファイルに書き、生成単位は 1 ファイルだけ読む
5. 3 帯は別コンテキスト・別 worktree（または別 clone）で実装する。単一樹の checkout 循環は不可
6. 提示は before+after の孤立 1 組を順に。採択前は意図帯を隠す
7. 最大化（「一番良い 1 案に寄せる」）をしない

## 6. 関連研究との関係

- **ヒューリスティック評価**（Nielsen & Molich, 1990; Nielsen, 1994）は欠陥の列挙である。TOC のフロアに使う。美的帯の占有は扱わない。
- **デザイン批評**（Schön, 1985; Alabood et al., 2023）は質的フィードバックの型を与える。TOC は批評を 3 値帯と生成契約に圧縮する。批評の豊かさは捨てる。その代わり再実行できる。
- **美学と HCI**（Tractinsky, 2004）は、美が意思決定に効くことを示す。TOC は美の普遍尺度を提案しない。依頼クラス \(R\) の下での帯の較正だけを扱う。
- **LLM-as-Judge とルブリック**（Hashemi et al., 2024; LangChain の較正指針）は、アンカーと人間補正を要求する。TOC の金標準 12 はそこに合わせる。3 値がより強いという主張はこれらの文献に帰属させない。
- **モード崩壊と多様性**（Zhang, Yu, Chong, et al., 2025）は、典型性バイアスで出力が一つに寄ることを示す。TOC は多様性一般ではなく、**順序付き三帯の占有** を目標にする。多様だが全部 \(G\) なら不採択である。
- **生成 UI ベンチマーク** の多くは「より高い一点スコア」を競う。TOC は一点スコアの最大化を、\(R\) に対する失敗モードとして明示的に捨てる。

---

## 7. 妥当性への脅威

**構成概念。** 三帯は日本語の日常評定に由来する。他言語へ訳すと間隔が崩れる。公式名を訳さず、§2 の操作的定義で評定する。

**評定者効果。** 内部評定者は自社の「いつもの良さ」に寄る。3 人のうち外部 \(\ge 1\) を必須にする（既定は内部 2 + 外部 1）。ブランド条項は 1 枚シートとフロア検査に切り出した。それでも文化圏が同じなら \(G^\star\) の閾値は共有バイアスを残す。

**画面サンプリング。** 改訂用 30 + holdout 10 + 予備 10 の層分けは偏りを減らすためであり、母集団の無作為標本ではない。TOC 名乗りは holdout ゲートである。改訂用 30 への再適合だけでは名乗らない。差し替えは予備 1 回までである。

**順序効果。** 同一の帯評定者が 3 after を順に見るため、先行 after が後続の \(H\) をずらす。ラテン方格と、三帯それぞれの位置差ゲートは平均の偏りを見る。残差のキャリーオーバーは残る。after ごとに独立な評定者を割る設計は、本稿の帯評定者 3 人制約の外である。

**エージェント / モデル依存。** 較正はモデル ID を固定して行う。ID が変わったら §4.5 を取り直す。

**作者汚染。** 生成者と帯評定者を分ける。評定前の手直しを禁止する（§4.5 手順 4）。

**検出力。** \(N=30\) 固定は小さい。ブートストラップの \(\gamma\) は、独立ラベル仮定の偽の狭さより、試行を単位にした幅を見るためである。見たあとで \(N\) を足してゲートを通してはならない。

**時間。** 視覚流行が変わると、今日の \(G^\star\) が翌年のテンプレ美＝\(F\) になる。アンカーは陳腐化したら入れ替える。スキル本文に年月で切れる流行リストを書かない。

**倫理。** \(G^\star\) は操作的魅力を上げ得る。§2.1-7 と 3 により、ダークパターンと a11y 犠牲は \(F\) である。TOC は説得の最大化手法ではない。

---

## 8. 限界

- 本稿は手法の提案であり、改訂用 30 も holdout 10 の採択データも持たない。未測定の実装を成果として扱ってはならない
- 改訂用 30 に再適合したスキルが holdout で落ちることは、想定される失敗である
- 三帯は、壊れていない改善の中での分割である。ユーザーテストの課題成功率、保持、売上は測らない
- \(G^\star\) はオンデマンドに保証できない。スキルが保証するのは手続と、較正後の占有指標である
- ネイティブ専用と、ブラウザで開けない機密画面は、実行時証拠があっても \(R\) からも較正からも外す
- ソースが git 作業樹に無い URL だけの依頼は \(R\) ではない
- 依頼が \(R\) でないとき（機能追加、ブランド新造、アクセシビリティ監査だけ）に TOC を適用してはならない

---

## 9. 結論

「もっといい感じにして」に対する良いスキルは、一点の最大美ではない。壊れていないことをフロアにしたうえで、**悪くない / まあまあ良い / めちゃくちゃ良い** を平均して均等に受領される 3 出力束を出せることである。

それを書く手順は短い。

1. 帯を語感ではなく、顔・横断・テーゼ・フロアで定義する
2. 1 束の意図は三帯を一つずつにする
3. 差は 4 軸の契約として書き、独立に実装する
4. 較正は改訂用 30 のあと holdout 10。改訂用は A/B/\(\hat{q}_{\mathrm{inc}}\)/位置差、holdout は \(|n_k-N_c|\le 2\)・\(n_\tau\ge 5\)・\(\hat{q}_{\mathrm{inc}}\) を `scripts/toc_gate.py`（付録 C）で判定する
5. `laststance/skills` の包装規約に載せ、未較正を較正済みと書かない

実装者は §5.5 の 7 拘束を `SKILL.md` に残し、§4.5 を回す。採択の前に帯名を依頼者へ見せない。これが、均等をスローガンではなく指標にする、ということである。

## 付録 C. `toc_gate.py` の正本

スキル実装時、次を `scripts/toc_gate.py` に置く。較正の採択数値はこの出力だけを使う。

入力 JSON:

```json
{"N": 1, "incomplete": 0, "completed": [
  {"t": 0, "view": [["G*", "G", "G-"], ["G", "G-", "G*"], ["G-", "G*", "G"]]}
]}
```

上は `view` の形状例である。`N=30` では `len(completed) + incomplete = 30` でなければならない。

JSON の帯記号は `G*` / `G` / `G-` だけ（本文の \(G^\star / G / G^-\)）。`t` は凍結画面番号（0 始まり）。`view[r][p]` は評定者 \(r\) が提示位置 \(p\) で付けた個人評定（三帯または `F`。個人 `U` は禁止）。多数決 `labels` は入力に書かない。スクリプトが方格 \(\mathrm{BASE}[r][(p+t)\bmod 3]\) で after に集約する。I 順に並べた view を渡してはならない。`incomplete` は生成不全 + 評定不全。`completed` は `t` の昇順。昇格予備も凍結時の \(t\) のまま。\(N\ge 30\) のときだけブート条項を A/B に入れ、位置差をゲートに入れ、A は \(\varepsilon=0.08\)、B は \(\hat{\tau}\ge 0.45\)。\(N<30\) では位置差を `ok` に入れず、A は \(|n_k-N_c|\le 2\)、B は \(n_\tau\ge 5\) である。

```python
# toc_gate.py — paper appendix C. numpy>=1.22 required.
import json, sys
import numpy as np

EPS, GAMMA, TAU0, QINC, POSD, B, SEED = 0.08, 0.15, 0.45, 0.10, 0.15, 2000, 20250911
LABS = ("G*", "G", "G-")
VIEW_OK = LABS + ("F",)
IDS = (("Ym", "Y", "Ys"), ("Y", "Ys", "Ym"), ("Ys", "Ym", "Y"))

def p_hat(labels):
    n = len(labels)
    if n == 0:
        return np.array([np.nan, np.nan, np.nan])
    return np.array([labels.count(k) / n for k in LABS])

def maxdev(ph):
    return float(np.max(np.abs(ph - 1.0 / 3.0)))

def majority(xs):
    from collections import Counter
    c = Counter(xs).most_common()
    if len(c) >= 2 and c[0][1] == c[1][1]:
        return None
    return c[0][0]

def labels_from_view(t, view):
    buckets = {"Ym": [], "Y": [], "Ys": []}
    for r in range(3):
        for p in range(3):
            buckets[IDS[r][(p + t) % 3]].append(view[r][p])
    labs = [majority(buckets[k]) for k in ("Ym", "Y", "Ys")]
    if any(x is None or x not in LABS for x in labs):
        raise ValueError("completed trial has F/U/tie; move to incomplete")
    return labs

def check_trial(row):
    view = row["view"]
    if "t" not in row:
        raise ValueError("t required")
    if len(view) != 3 or any(len(x) != 3 or any(v not in VIEW_OK for v in x) for x in view):
        raise ValueError("view must be 3x3")

def main(path):
    d = json.load(open(path))
    N = d["N"]
    trials = sorted(d["completed"], key=lambda r: r["t"])
    ts = [r["t"] for r in trials]
    if len(ts) != len(set(ts)):
        raise ValueError("duplicate t")
    if d["incomplete"] + len(trials) != N:
        raise ValueError("incomplete + completed must equal N")
    for t in trials:
        check_trial(t)
    qinc = d["incomplete"] / float(N)
    nmin = int(np.ceil(0.9 * N))
    q_ok = qinc <= QINC
    n_ok = len(trials) >= nmin
    if not n_ok:
        json.dump(
            {"ok": False, "q_inc": qinc, "A": None, "B": None, "pos": None},
            sys.stdout,
        )
        return
    packed = [labels_from_view(t["t"], t["view"]) for t in trials]
    labs = [x for row in packed for x in row]
    ph = p_hat(labs)
    perm_n = int(sum(set(row) == set(LABS) for row in packed))
    tau = perm_n / float(len(packed))
    views = np.array([t["view"] for t in trials])
    posd = float(
        max(
            np.max(r) - np.min(r)
            for r in (np.mean(views == k, axis=(0, 1)) for k in LABS)
        )
    )
    use_boot = N >= 30
    pos_ok = True if N < 30 else posd <= POSD
    nc = len(packed)
    counts = [labs.count(k) for k in LABS]
    a_ok = maxdev(ph) <= EPS if use_boot else all(abs(c - nc) <= 2 for c in counts)
    b_ok = tau >= TAU0 if use_boot else perm_n >= 5
    if use_boot:
        rng = np.random.Generator(np.random.PCG64(SEED))
        nc = len(trials)
        idx = np.arange(nc)
        md, tb = [], []
        for _ in range(B):
            take = rng.choice(idx, size=nc, replace=True)
            sl = [packed[i] for i in take]
            md.append(maxdev(p_hat([x for t in sl for x in t])))
            tb.append(np.mean([set(t) == set(LABS) for t in sl]))
        a_ok = a_ok and float(np.percentile(md, 95, method="linear")) <= GAMMA
        b_ok = b_ok and float(np.percentile(tb, 2.5, method="linear")) > 2.0 / 9.0
    ok = q_ok and n_ok and a_ok and b_ok and pos_ok
    json.dump(
        {
            "ok": bool(ok),
            "q_inc": qinc,
            "p": ph.tolist(),
            "tau": tau,
            "n_tau": perm_n,
            "posd": posd,
            "A": bool(a_ok),
            "B": bool(b_ok),
            "pos": bool(pos_ok),
        },
        sys.stdout,
    )

if __name__ == "__main__":
    main(sys.argv[1])
```

NumPy `method="linear"` は Hyndman–Fan 型 7 である。`krippendorff` はゲート α 専用であり、本スクリプトには含めない。

## 付録 D. `toc_alpha.py` の正本

`krippendorff==0.8.2` をピンする。金標準は 3×9、本測定の報告用は 3×\(3N_c\)（after 単位。位置順禁止）。値は `0` (`G-`), `1` (`G`), `2` (`G*`), 欠測は `null`。8/9 と 10/12 は同じファイルに `items`（12 件。各 `gold` と `votes` 3）を渡したときの出力だけを使う。

入力が配列なら本測定報告用の α だけ（`ok` は `null`。0.67 判定はしない）。金標準ゲートは `{items: [...12]}` だけを渡し、`reliability` は帯 9 の `votes` からスクリプトが組む。手渡し行列は使わない。`ok` は金標準の 3 ゲートが揃ったときだけ真偽になる。

```python
# toc_alpha.py — paper appendix D.
import json, sys
from collections import Counter
import numpy as np
import krippendorff

LABS = ("G*", "G", "G-")
OK = LABS + ("F",)

def majority5(votes):
    c = Counter(votes).most_common()
    if len(c) >= 2 and c[0][1] == c[1][1]:
        return "U"
    return c[0][0]

def gold_ok(items):
    if len(items) != 12:
        raise ValueError("items must be 12")
    if sum(x["gold"] == "F" for x in items) != 3:
        raise ValueError("need exactly 3 F golds")
    band = [x for x in items if x["gold"] in LABS]
    if len(band) != 9:
        raise ValueError("need 9 band golds")
    for x in items:
        vs = x["votes"]
        if x["gold"] not in OK or len(vs) != 3 or any(v not in OK for v in vs):
            raise ValueError("votes")
    band_ok = sum(majority5(x["votes"]) == x["gold"] for x in band)
    fnf_ok = 0
    for x in items:
        m = majority5(x["votes"])
        if m != "U" and (m == "F") == (x["gold"] == "F"):
            fnf_ok += 1
    return band_ok, fnf_ok, band

def rel_from_band(band):
    enc = {"G-": 0, "G": 1, "G*": 2}
    rel = []
    for r in range(3):
        row = []
        for x in band:
            v = x["votes"][r]
            row.append(enc[v] if v in enc else None)
        rel.append(row)
    return rel

def main(path):
    raw = json.load(open(path))
    if isinstance(raw, list):
        rel, items = raw, None
    else:
        if "reliability" in raw:
            raise ValueError("omit reliability; built from items")
        items = raw["items"]
        _, _, band = gold_ok(items)
        rel = rel_from_band(band)
    data = np.array(rel, dtype=float)
    a = krippendorff.alpha(
        reliability_data=data,
        level_of_measurement="ordinal",
        value_domain=[0, 1, 2],
    )
    out = {"alpha": float(a), "ok": None}
    if items is not None:
        band_ok, fnf_ok, _ = gold_ok(items)
        out["band_ok"] = band_ok
        out["fnf_ok"] = fnf_ok
        out["ok"] = bool(a >= 0.67 and band_ok >= 8 and fnf_ok >= 10)
    json.dump(out, sys.stdout)

if __name__ == "__main__":
    main(sys.argv[1])
```
