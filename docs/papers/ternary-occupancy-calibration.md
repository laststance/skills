# 三元占有較正によるデザイン改善スキルの構築法

**Ternary Occupancy Calibration for Design-Improvement Agent Skills**

人間が Web サイト / GUI アプリに対して「もっといい感じにして」と依頼したとき、3 出力の人間評定が平均して **めちゃくちゃ良い** / **まあまあ良い** / **悪くない** に均等へ向かうスキルを、どう設計し、どう検証し、どう包装するか。

- 文書種別: 手法論文（method paper）。大規模被験者実験の結果報告ではない
- 対象読者: エージェントスキル作者、デザインエンジニア、評価設計者
- 実装先規約: `laststance/skills`（`SKILL.md` + 遅延ロード、エージェント非依存が既定）
- 用語の正本: 品質帯の公式名は日本語ラベル。英語グロスは補助

---

## 要旨

「もっといい感じにして」は、成功条件が数値化されていない依頼である。現行のコーディングエージェントは、この依頼を **単一の最良改善** へ畳み込みやすい。その結果、出力は次の二極にモード崩壊する。

1. **安全な中央値** — 既存トークンを少し整えただけの「まあまあ良い」
2. **偽の頂点** — Inter / 大きな角丸 / 紫グラデ / 汎用 shadcn 美に寄った「めちゃくちゃ良い」風

どちらも、依頼者の選択を狭める。本稿の主張は、品質を最大化することではない。**1 回の依頼に対して 3 つの実装済み改善を束（bundle）として出し、人間が各出力を独立に評定したとき、三つの日本語品質帯の出現頻度が平均して均等に近づくスキル** を構築する手順を与えることである。

三帯はいずれも「壊れていない」より上に置く。

| 公式ラベル | 記号 | 英語グロス | 依頼者が口にする反応の目安 |
|---|---|---|---|
| めちゃくちゃ良い | \(G^\star\) | delight | 「これ、人に見せたい」 |
| まあまあ良い | \(G\) | solid | 「ちゃんとしたデザイナーが通った」 |
| 悪くない | \(G^-\) | acceptable | 「これなら出していい / 無難に良くなった」 |

生成時、スキルは各出力に **意図バンド** \(I\) を一つ割り当てる（1 束で三帯を一つずつ）。検証が測るのは \(I\) そのものではなく、評定者が \(I\) を知らずに付ける **受領評定** \(H\) の分布である。\(I=H\) の完全一致は診断用の混同行列であり、採択条件ではない。ラベルを出力に印刷してから同じラベルを付けさせる手続は、均等をトートロジーにするので禁止する。

採択は次である（定義は §4.2）。

- **周辺一様性 (A)**: \(\max_k|\hat{p}_k-1/3|\le\varepsilon=0.08\)。改訂用 30 ではさらにブートストラップ 95%点 \(\le\gamma=0.15\)
- **バンドル置換率 (B)**: \(\hat{\tau}\ge\tau_0=0.45\)。改訂用 30 ではさらにブートストラップ 2.5%点 \(>2/9\)
- **不全率**: \(\hat{q}_{\mathrm{inc}}\le 0.10\)
- **位置差**: 個人評定の位置別 \(P(H=G^\star)\) の幅 \(\le 0.15\)。**改訂用 30 だけ**

holdout 10 の A/B は点推定だけである。位置差もブートも holdout には課さない。

本稿は実験結果を報告しない。代わりに、スキル作者が実装し、評定し、棄却または採択できる手続きを固定する。

## 1. 導入

### 1.1 依頼クラス \(R\)

本稿が扱う依頼は、次をすべて満たす発話およびその言い換えである。

- 対象が **既に存在する** Web サイトまたは GUI アプリの、**名前付き 1 画面** である（ゼロからのブランド策定は外）
- その画面は URL と到達状態（ログイン、クエリ、開いたパネル）で指せる
- 対象画面のソースが、エージェントの **git 作業樹**（または同等の clone）として開かれている
- 依頼者が求める変化は **見た目と操作感の質** である（新機能追加は主目的ではない）
- 成功条件は「もっといい感じ」「なんかダサい」「polish して」など、**評定可能だが数値化されていない**

このクラスを \(R\) と書く。1 回の \(R\) 実行は **1 画面 → 1 束** である。サイト全体への依頼は、画面ごとの TOC 実行を並べる。サイト全体を 1 束で再スタイリングすることは対象外である。

### 1.2 単一出力最大化の失敗

\(R\) に対して「最善の 1 案」を出すスキルは、次の理由で依頼者の役に立ちにくい。

- **嗜好はスカラーではない。** 同じ画面でも、保守的な出荷と、記憶に残る再設計では、採用条件が違う。
- **典型性バイアス。** 選好学習を経たモデルは、よくある「良い UI」へ収束する（Zhang et al., 2025）。デザインではそれが Inter・大きな radius・紫アクセント・汎用カードグリッドとして現れる。
- **中央収束。** 細かい絶対評定は中央に寄りやすい。本稿は帯を 3 値に固定する。
- **選択の欠如。** 依頼者はリスク許容度を後から決める。1 案は、その決定を先取りして潰す。

束サイズ 3 は、三帯を一つずつ置く最小整数である。4 以上の束は対象外とする。

### 1.3 本稿が答える問い

> スキル \(S\) をどう書けば、\(R\) に対する 3 出力束 \(Y = \{y_1, y_2, y_3\}\) を、人間評定 \(H(y) \in \{G^\star, G, G^-\}\) が **平均して均等** に付ける状態へ、作者が寄せられるか。

「平均して均等」の操作的定義は §4.2 に置く。

### 1.4 貢献

1. \(R\) に対する三帯の操作的定義と、帯に入らない **不合格** の分離（§2）
2. 意図バンドと受領評定を分離した **三元占有較正（TOC）** の手続（§3–§4）
3. 介入強度 4 軸による、帯漏れを減らす生成契約（§3.3）
4. 周辺一様性とバンドル置換率の二指標、標本サイズ、較正セット（§4）
5. `laststance/skills` へ落とす包装手順（§5）

## 2. 品質帯の操作的定義

評定はラベルの語感に頼らない。各帯は **観察可能な反応** と **禁止事項** で定義する。英語グロスは補助であり、公式名は置き換えない。

### 2.1 不合格（帯の外）

次のいずれかがあれば、その出力は三帯のどれにも入れない。記号は \(F\)。生成フロア、§2.6、金標準、倫理は **このリストだけ** を \(F\) と呼ぶ。

1. 機能退行（以前できた操作ができない、誤った状態表示）
2. 指定レンダー欠陥。正本は次の 6 種の判定文だけである。visual-lint コードは探索補助であり、第二の \(F\) リストではない。画素が判定文に当たれば \(F\)。6 種外（接触だけ、孤児語、化粧品、hover lift）は条項 2 にしない。

   | 種 | 判定文 | よく当たる visual-lint コード |
   |---|---|---|
   | 折り返し | 1 行であるべき語が 2 行以上 | A1, A7 |
   | 欠け | 必要なグリフまたは面が潰れて無い | D5、A6 の tofu / missing icon |
   | 重なり | 2 要素の画素が重なる。接触だけは重なりではない | A5 |
   | 切れ | 内容が枠で切断されている | A2, A3, B1, B3 |
   | 読めないコントラスト | 文字または必須 UI が地に沈む | E1, E2 |
   | ターゲット過小 | 操作可能なコントロールの当たりが見た目で 44px 未満 | D3 |
3. アクセシビリティ退行（フォーカス消失、コントラスト低下、動きの止め方の喪失、名前付けの喪失）
4. 第二のスタイリング系統の導入
5. 既存トークンを無視したワンオフ色・型・影
6. ブランド破壊（プロダクトがそう見えてはいけない見た目への勝手な転向）
7. ダークパターン、または注意の搾取
8. テンプレ美（偽の頂点: 紫グラデ、ガラスカードの量産、意味のない blob、Inter への無断置換など、よくある AI slop を「テーゼ」と偽る）
9. 散らかった改変: 決断 0 かつ顔局所数が 2 以上かつ統一原則なし
10. 言えるテーゼが 2 つ以上ある
11. 観察可能な改善が 0。判定は視覚だけである。before と after を孤立提示し、3 秒で画素上の違いを 1 つも言えない。git diff は使わない。見えない属性だけの after は 11。見えるコピー変更やフォーカスリング追加は 11 ではない

**統一原則** の正本は §2.4 である。ここでの言い換えは使わない。

\(F\) は「悪くない」ではない。**悪くないは、壊れていない上での控えめな改善** である。

**顔** の次元は次の 7 つに固定する。ヒーローやナビは骨格レイアウトの例であり、別次元ではない。

キーカラー / 骨格レイアウト / タイプ骨格 / 反復モチーフ / リズム / モーション原則 / 素材

### 2.2 \(G^-\) 悪くない（acceptable）

**何をする帯か。** 欠陥と、誰が見ても雑なクラフトだけを上げる。新しい美的テーゼは出さない。既存の視覚言語の内側に留まる。

**観察可能な印。**

- 変更 diff は局所（色の 1 段階、余白の揃え、角丸の同心、欠け修正、状態色の不足分）
- 顔 7 次元の **決断は 0**。顔局所は高々 1 次元
- 統一原則表の同一規則の解消点が 3 以上なら \(G\) であり \(G^-\) ではない。色の 1 段階は表に無いので、何点でも \(G^-\) のまま（決断 0 のとき）
- 依頼者が before/after を 3 秒見比べて、「前よりマシ。説明は要らない」と言える

**生成契約上の禁止**（H の木には出さない）: 新しいフォントファミリー、新しいキーカラー、レイアウト原則の変更、装飾モーションの追加。

### 2.3 \(G\) まあまあ良い（solid）

**何をする帯か。** 既知のクラフトを、画面の支配的な表面に対して漏れなく適用する。新しい「見た目の主張」は持たないが、プロの手が通った密度になる。

**観察可能な印。**

- タイプスケール、余白リズム、階層、空状態 / エラー / ローディング / 無効が揃っている
- 既存トークンの範囲で、影・境界・半径・アイコンウェイトが一貫する
- 依頼者が「特別ではないが、出荷して恥ずかしくない」と言える
- 変更は局所パッチの集合ではなく、**同一原則の横断適用** に見える

**生成契約上の禁止**（H は木だけ）: 未所持モチーフの導入。「一発で覚える画面」を狙うこと。before に 0 点の規則を 2 点以上入れること（それは \(G^\star\) の決断である）。\(I=G\) が使ってよい統一原則は、before に 1 点以上ある規則だけである。

### 2.4 \(G^\star\) めちゃくちゃ良い（delight）

**何をする帯か。** 制約の内側で、**ちょうど一つのテーゼ** を通す。

各顔次元は before と比較して次の **ちょうど 1 水準** を取る。水準は 3 つだけである。

| 水準 | 判定文 |
|---|---|
| 不変 | その次元にクラフト上の変化が無い |
| 局所 | クラフト上の変化はあるが、強制問はいいえ |
| 決断 | 強制問がはい |

**条項 2 修復** は、同じトークン・同じ原則のまま §2.1 条項 2 の 6 種だけを直した変更である。トークンまたは原則も変わった変更は、6 種が同時に直っていても条項 2 修復ではない。条項 2 の「欠け」（グリフ / 面の欠損）と統一原則の「欠け」（表規則が通っていないこと）は別物である。条項 2 修復は顔次元を動かさない。顔の水準も顔局所数も変えない。

**クラフト上の変化** は、その顔次元について before と after で次のいずれかが違うことである。(a) 使っているトークン名 (b) その次元の原則（揃え方、スケール段、反復の有無） (c) 色の 1 段階。条項 2 修復はクラフト上の変化ではない。

**強制問**（各次元について、この文だけを使う）: 「この次元で、before に無かった新しい原則または新しいトークン系統を、顔 7 語から 1 つで言え、その反復箇所を 2 点以上指せるか。」はい → 決断。いいえ、かつその次元にクラフト上の変化がある → 局所。クラフト上の変化が無い → 不変。既存規則の横断は、before にその規則の適用が 1 点でもあれば新しい原則ではない。before にタイプスケール / 余白リズムの適用が 0 点なら、それを導入して反復 2 点以上は決断である。条項 2 修復はクラフト上の変化ではない。

**色の 1 段階** は、プロジェクトの既存スケール（Tailwind 番号、デザイントークンの隣ストップ）で、同じ色役割を隣へ 1 つだけ動かすことである。スケールが無いときは、同じ色相のまま明度を一段だけ変える。色相変更、役割の新設、パレット外 hex は 1 段階ではない。1 段階は反復 2 点以上でも決断ではない。色役割の変化は顔次元 **キーカラー** に載せる。ただし状態色（成功 / エラー / 警告 / 情報）の不足を **既存の状態トークン** で足すことはキーカラーの決断ではない。顔局所数に足さず、状態揃えの解消点にだけ数える。

**テーゼ数** は決断水準の次元数。**統一原則** は次をすべて満たすときにだけ成立する。決断数 0、次表の規則のうち **少なくとも 1 つ** が支配的表面に解消点 3 以上ある。複数の規則が同時に解消点 3 以上でも統一原則である（§2.3 の総動員は \(G\)）。どれも解消点 3 未満、または決断数が 1 以上なら統一原則ではない。

| 統一原則の規則名 | 載せる場所 |
|---|---|
| タイプスケール | 顔: タイプ骨格 |
| 余白リズム | 顔: リズム |
| 同心半径 | 顔: 素材 |
| アイコンウェイト | 顔: 反復モチーフ |
| 状態揃え | 非顔（顔局所数に足さない） |

**点** は最も外側のコンポーネントインスタンス 1 つである。カード、グリッドセル、テーブル行、フォーム行、リスト行、見出し+本文の組は各 1 点。内側のボタンやアイコンは数えない。CSS 変数を 1 箇所変えて N 個に効いても N 点。

**欠け** は、その規則が通っていない外側インスタンス 1 つを 1 点とする。**基準値** は、同じ役割の外側インスタンスのうち、その規則のトークンまたは間隔として最も多い値である。同数のときは DOM 順（上から、同列なら左から）で先に現れる値。**不揃え** は、規則は通っているが基準値と目視で違う外側インスタンス 1 つを 1 点とする。欠けは不揃えに二重カウントしない。**解消点**（密度が上がった）は、before で欠けまたは不揃えだったインスタンスが、after でその規則が通り、かつ同じ役割の after 基準値と目視で一致した数である。

統一原則の 3 点は解消点だけである。before から既に基準値へ揃っていたインスタンスと条項 2 修復は数えない。トークンまたは原則を変えて表規則を通した変更は条項 2 修復ではないので、解消点に数える。余白リズム三帯と §2.2 / §3.3 の「3 点」もこの解消点である。

凍結 40 の入場条件は次の 1 文だけである。支配的表面に外側インスタンスが 3 以上あり、統一原則表の同一規則について、before にその規則の適用が 1 点以上あり、かつ欠けまたは不揃えがその規則で 3 点以上ある。

**支配的表面** は **画面 1 つにつき 1 つ** である。較正では生成より前に、before に対して CSS セレクタ 1 つと、その要素のビューポート矩形を凍結表へ書く。3 after と G 契約は、この同じ指し示しを使う。after でセレクタが要素ちょうど 1 つに解決すればそれを使う。0 または 2 以上なら、凍結矩形と交わる本文に、セレクタ成功時と同じ点の定義を適用する。グリッドが見えるなら枚数だけ数える。ラッパー 1 つに畳まない。ナビ・クロームは含めない。開いたモーダルがあるときはその本文ノードを書く。実行時は、開いたダイアログ本文、なければ `main`、なければ親が選んだ本文ブロック 1 つを帯契約に書く。これ以外の面積アルゴリズムで測り直してはならない。

較正セットの入場は上の 1 文だけである。実行時に点が 3 未満でも \(I=G\) は禁止しない。

同一画面での余白リズム三帯（金標準の境界でもこれを使う）:

- \(G^-\): 余白リズムの解消点 1–2。リズムは局所。決断 0。統一原則なし
- \(G\): 余白リズムの解消点 3 以上。リズムは局所。決断 0。統一原則 = 余白リズム
- \(G^\star\): 余白リズムを製品の武器にする新しい原則。リズムは決断

ステップ 3 の「顔局所数」は、水準が局所である顔次元の数である。非顔の修正（状態色など）は顔局所数に足さない。状態揃えの解消点には数える。

**観察可能な印。**

- 3 秒で「何を決めた画面か」が言える
- その決断が、画面の複数箇所に反復され、一貫している
- 依頼者が「好き嫌いは分かれるが、見せる価値がある」と言える
- 既存トークン・アクセシビリティ・ブランドのハードフロアは守っている

**禁止。** テンプレ美の移植。テーゼが 2 つ以上。§2.1 の 1–7 を「美しさ」のために割ること。

### 2.5 帯は順序を持つが、採用価値は順序ではない

クラフト上の野心は \(G^\star > G > G^-\) である。出荷価値は依頼者のリスク許容度に依存する。均等占有は、スキルが依頼者の代わりにリスクを先取りしないための設計である。

### 2.6 帯判定（全域関数）

評定者と較正セット作成は、同じ木を上から一度だけ辿る。本測定の \(H\) もこの木である。帯ごとの生成禁止は H に直接出さない。H の正本は木である。`judge-tree.md` は次をこの順で載せる。(1) 顔 7 語と「ヒーロー / ナビは骨格レイアウトの例」 (2) §2.1 の 11 条と条項 2 表 (3) §2.4 の水準表・条項 2 修復・強制問・クラフト上の変化・色の 1 段階・統一原則表・統一原則の成立文・点・欠け・基準値・不揃え・解消点・支配的表面・余白リズム三帯 (4) §2.6 の木 0–6。依頼者の反応目安、生成契約上の禁止、§2.5 は載せない。これ以外を配布しない。どの入力も次の最初に当たった葉へ落ちる。

0. 7 次元を不変 / 局所 / 決断に分け、テーゼ数と統一原則を §2.4 で確定する
1. §2.1 の 1–8 または 11 のいずれか → \(F\)
2. テーゼ数が 2 以上 → \(F\)（§2.1-10）
3. 決断 0 かつ顔局所数が 2 以上かつ統一原則なし → \(F\)（§2.1-9）
4. テーゼ数がちょうど 1 → \(G^\star\)
5. 決断 0 かつ統一原則がある → \(G\)
6. それ以外 → \(G^-\)

ステップ 4 が \(G^\star\) の唯一の入口。ステップ 5 が \(G\) の唯一の入口。ステップ 6 は決断 0・統一原則なし・顔局所数 0 または 1 で、11 でもない葉である（非顔だけの局所修正を含む）。

## 3. 三元占有較正（TOC）

### 3.1 対象と非対象

**対象。** 依頼クラス \(R\) に応じる **生成スキル** の書き方と、その較正。既存画面を読み、3 つの実装済み改善を出す。

**非対象。**

- 欠陥検出だけの監査（`/visual-lint`, `/ux-gap-detector`）
- ゼロからのデザインシステム策定
- 「常に最高にしろ」という単一出力スキル
- ソースリポジトリが無く、URL のオーバーレイだけを出す依頼
- 人間の趣味そのものの普遍化

### 3.2 意図と受領の分離

各出力 \(y_i\) は生成時にちょうど一つの **意図バンド** \(I(y_i) \in \{G^\star, G, G^-\}\) を持つ。1 束は意図の上では必ず三帯を一つずつ含む。

\[
\{I(y_1), I(y_2), I(y_3)\} = \{G^\star, G, G^-\}
\]

評定者は \(I\) を見ない。同一の帯評定者 3 人が、各 \(y\) を **before + その after だけ** で順に見る（横並び同時提示は禁止）。多数決後の \(H(y) \in \{G^\star, G, G^-, F, U\}\) を付ける。生成不全は評定しない。評定不全（多数決に \(F\) または \(U\)）は指標 A/B から除外する。どちらも §4.4 の \(\hat{q}_{\mathrm{inc}}\) に数える。

成功は \(I = H\) の完全一致を要求しない。成功は §4.2 のゲートである。

### 3.3 介入強度の 4 軸

帯の差は **変更してよい範囲の契約** として書く。軸は 4 つ。各軸は順序尺度であり、数値の絶対値に意味はない。

| 軸 | \(G^-\) | \(G\) | \(G^\star\) |
|---|---|---|---|
| **範囲 (Scope)** | 局所。指摘された面、または欠陥のある面だけ | 支配的表面で同一規則の解消点 3 以上 | 顔の 7 次元のうち、テーゼにする一点 |
| **リスク (Risk)** | 既存視覚言語の内側 | 既存言語の密度を上げる。新モチーフは禁止 | 既存制約の内側で、一つの新しい決断を許す |
| **可逆 (Reversibility)** | 1 ファイル数行で戻せる | トークンまたは共通部品への横断だが、原則は増えない | 原則が一つ増える。戻すと顔が消える |
| **驚き (Surprise)** | 説明不要。差分は「修正」に見える | 説明は「原則の適用」で足りる | 説明は「何を決めたか」になる。テンプレ美は失格 |

スキル本文は、帯ごとにこの 4 軸を **やってよいこと** として書く。禁止の列挙だけにしない。

### 3.4 生成手続（作者がスキルに書く手順）

エージェントが \(R\) を受けたとき、手順 0–6 をこの順で行う。自己検査が \(F\) の案だけを捨て、同じ帯を取り直す。帯あたり試行は最大 3 回（初回 + 再生成 2）。\(H \neq I\) と「三出力が同じ顔」は再生成条件にしない。

**同じ顔。** 3 after それぞれについて、§2.4 と同じ 3 水準ベクトル（各顔次元が 不変 / 局所 / 決断）をステップ 0 と同一関数で書く。3 ベクトルが一致するとき同じ顔である。ゼロベクトルどうしも同じ顔。上の余白リズム三帯は \(G^\star\) だけが決断なので同じ顔ではない。

**実行時**（依頼者が 1 画面を投げた日常利用）: 3 回とも \(F\) の帯がある束、または三出力が同じ顔の束は **未完了** である。2 出力を TOC 束として渡してはならない。同じ顔の 3 after は見せてよいが、TOC 完了とは言わない。支配的表面の点が 3 未満でも意図三帯は出す。\(I=G\) は存在する点のすべてに既存規則を通す。\(H\) が \(G^-\) でも再生成しない。そのような画面は較正セットに入れない。較正の \(N\) や帯評定者は実行時に出さない。

**較正時**（§4）: 3 回とも \(F\) の帯がある束は **生成不全** として閉じ、評定に回さない。画面は凍結集合に残す。同じ顔は評定に回す。

**手順 0 — 証拠。** 対象画面の実行中 UI を見る。コードだけ、記憶だけで帯を割り当てない。スタイリング系統（Tailwind / CSS / CSS-in-JS）を特定し、第二系統を足さない。

**手順 1 — フロア。** 用語「フロア」は §2.1 の **1, 3–7** だけを指す。条項 2 は生成チェックに残すが、フロア検査の担当外である。フロア 1, 3–7 と条項 2 を 3 つの worktree 契約へ同じ文面で写す。共有 base commit に先に入れて 3 分岐してはならない。どの帯もフロアを免除されない。

**手順 2 — 現状の顔。** 画面がいま何で覚えられているかを、§2.1 の 7 次元で一文に書く。

**手順 3 — 帯契約の固定。** 静的ファイル `references/band-*.md` は 4 軸のテンプレである。オーケストレータが、この画面の語彙へ翻訳した契約を **各 worktree 局所** に 1 ファイルずつ書く。例: 「\(G^-\) はヒーロー内の Card 1 枚の半径だけ（共通トークンは触らない）」「\(G\) は余白リズムの解消点を支配的表面で 3 以上にする。新原則は足さない」「\(G^\star\) は骨格を密度優先に再編成する。キーカラーは触らない」。生成単位は、自分の worktree にある契約 1 ファイルだけを読む。静的テンプレ 3 つを同じコンテキストに読み込んではならない。

**手順 4 — 隔離生成。** 3 帯は **別コンテキスト・別 git worktree（または別 clone）** で実装する。同一会話で 3 バージョンを出すことを禁止する。実装は `Task` 3 本、または帯ごとに新しい会話 3 回。完了物は 3 worktree が残っていること。単一作業樹での checkout / revert 循環は「3 実装」に数えない。評定は 4 インスタンス（before + 3 after）を別ポートで起動できることを原則とする。ホストが同時 4 ポートを持てないときだけ、残してある 3 worktree を順に起動する。

**手順 5 — 自己検査。** オーケストレータだけが、ゲート通過後に凍結した `references/judge-tree.md` を読む。生成単位は読まない。親は after を 1 つずつ、\(I\) を隠して木を通す。**葉が \(F\) のときだけ** 同じ帯を再生成する（帯あたり最大 3 試行）。三出力が同じ顔なら記録する。再生成はしない。実行時は未完了。較正では評定に回す。

**手順 6 — 提示。** 依頼者には各 after を **before + その after だけ** で順に見せる。横並び 3 枚は禁止。意図ラベルは、較正が holdout を満たすまで出さない。動きを契約した帯は録画フレームを残す。

### 3.5 スキル本文に置くもの、開示するもの

**`SKILL.md` に残す（毎実行）。**

- 依頼クラス \(R\) の判定（1 画面 1 束）と、対象外
- 不合格 \(F\) へのポインタ（定義の正本は `judge-tree.md`。生成単位は読まない）
- 手順 0–6 の **実行時** 完了条件。手順本文は `workflows/generate-bundle.md` にだけ置く
- 「帯契約ファイルは 1 実行単位につき 1 つだけ読む」
- 3 出力を意図三帯で閉じること。実行時に帯が 3 回 \(F\)、または同じ顔なら未完了
- 較正の \(N\)・評定者・ブートストラップは `SKILL.md` に置かない（`references/calibration.md`）

**遅延ロード（生成単位は自分の帯ファイルだけ）。**

- `references/band-g-minus.md` / `band-g.md` / `band-g-star.md`
- `references/anchors.md`（較正セット。作者用）
- `references/confusion-repair.md`（作者用）
- `references/calibration.md` と `scripts/toc_gate.py`（実行時エージェントは見ない）

`description` は第三人称で、**何をするか** と **いつ使うか** を両方書く。トリガー語に「もっといい感じ」「polish」「feel better」「ダサい」を含める。

### 3.6 既存 laststance スキルとの位置

| スキル | 問うこと | TOC との関係 |
|---|---|---|
| `/visual-lint` | レンダーは壊れているか | 条項 2 の探索補助。フロア検査（1, 3–7）ではない。表外の指摘は \(F\) にしない |
| `/ux-gap-detector` | SaaS 内面の UX ギャップは何か | 入力の候補。帯は持たない |
| `/product-inspiration` | 上位アプリは何をしているか | \(G^\star\) のテーゼ探索に使える。移植そのものは偽の頂点 |
| 単一出力の design-review 系 | 美的に良いか、そして直せ | 最大化スキル。TOC とは目的が違う |

TOC スキルはこれらを再実装しない。**3 帯の占有** だけを自分の仕事にする。

## 4. 検証手続

### 4.1 評定プロトコル

**評定単位。** 1 試行 = 名前付き 1 画面（URL + 到達状態）+ before 1 + after 3。同じ URL+状態を 2 束目に使わない。

**孤立提示。** 同一の帯評定者 3 人が、各 after を **before + その after だけ** で順に見る。横並び 3 枚は禁止。提示順は試行内ラテン方格に固定する。基本方格の行は \((Y^-,Y,Y^\star)\)、\((Y,Y^\star,Y^-)\)、\((Y^\star,Y^-,Y)\)。試行番号 \(t\)（凍結画面番号、0 始まり）で列を \(t \bmod 3\) 左回転し、行を評定者 0,1,2 に割り当てる。

**独立評定。** 各 after に §2.6 で \(H \in \{G^\star, G, G^-, F\}\) を付ける。三帯を一つずつ割り当てる強制割当は使わない。

**役割の分離。**

- **生成者** は評定しない。\(I\)、プロンプト、生成ログを評定者に渡さない
- **フロア検査** は 1 名。帯評定も生成も兼ねない。本測定で §2.1 の **1, 3–7** を付ける。ここが \(F\) ならその出力は \(F\) で確定する
- **帯評定者** は 3 人（外部 1）。フロア非 \(F\) の出力に対し木をステップ 1 から付ける（2, 8–11 と、フロアの見落とし）

| 番号 | 本測定 | 金標準 |
|---|---|---|
| 1, 3–7 | フロア検査が先。見落としは帯評定のステップ 1 | 帯評定 3 者だけ |
| 2, 8–11 | 帯評定 3 者だけ | 帯評定 3 者だけ |

指標 A/B のラベルは帯評定 3 者の **多数決** である。多数が無い出力は \(U\)。その試行は評定不全。

**ブラインド。** 帯評定者は \(I\)、生成プロンプト、生成ログ、作者予想を見ない。

**較正セット。** 生成より前に行う。金標準 12 件は before + after。凍結 40 の URL+状態と互いに素。評定者配布物は `judge-tree.md` と、各画面の支配的表面の指し示しだけ。帯 9 件（各帯 3）のうち、余白リズムが決断になる境界と統一原則になる境界を 1 件ずつ、色の 1 段階が局所になる境界を 1 件含める。\(F\) 3 件は (a) 11 をちょうど 1 件、(b) \(\{8,9,10\}\) から 1 件、(c) \(\{1{-}7\}\) から 1 件。ラベルは生成者以外の 2 名以上がゲート前に凍結する。ゲート失敗でラベルを書き換えて通してはならない。

木の注釈を足したら次をこの順で行う。(1) 同じ金標準 12 を同一 3 者が再評定し、3 ゲートを取り直す。(2) 改訂用 30 の生成物と評定は、済んでいても捨て、同じ凍結 URL で再生成し 4 ゲートを取り直す。holdout の生成物と評定も済んでいても捨てる。holdout の再生成と評定は手順 7 まで行わない。(3) holdout の評定が一度でも済んでいたら TOC 名乗りは無効であり、その URL+状態は再利用禁止、新しい holdout 10 を層 3:1 が保たれるよう先に凍結する。未評定ならその URL を残す。どちらも手順 7 まで holdout を生成しない。それでもゲートが落ちるなら新しい 12 件を凍結からやり直す。

\(\alpha\) は `scripts/toc_alpha.py`（付録 D）だけを使う。符号化 \(G^-=0,\ G=1,\ G^\star=2\)。金標準帯への \(F\) はそのセルだけ `nan`。

ゲートは次の 3 つをすべて満たすこと。

- 帯 9 件の \(\alpha\)（順序 \(G^- < G < G^\star\)）\(\ge 0.67\)
- 帯 9 件の正答: 多数決ラベルが凍結金標準帯と一致する件数が \(\ge 8\)
- 12 件の \(F\) / 非 \(F\) 正答: 多数決の「\(F\) か否か」が凍結金標準と一致する件数が \(\ge 10\)

**LLM ジャッジ。** 人間金標準との一致を出さずに TOC 成功を主張してはならない。

### 4.2 「平均して均等」の指標

指標 A/B は母集団推論ではなく、**事前固定した 30 画面に対するスキル成果物の採択ゲート** である。見たあとで標本を足さない。

**凍結条件** は次の組である。改訂用画面 30、holdout 画面 10（改訂用と互いに異なる URL+状態）、各画面の支配的表面ポインタ、モデル ID、デコード、道具、スキルハッシュ、定数 \(\varepsilon=0.08\), \(\gamma=0.15\), \(\tau_0=0.45\), \(\hat{q}_{\mathrm{inc}}\) 上限 \(0.10\), 位置差上限 \(0.15\), ブートストラップ回数 \(2000\), 種 `20250911`。データ閲覧後に定数を動かして TOC を名乗ってはならない。モデル ID が変わったら §4.5 を最初から取り直す。

TOC を名乗るのは holdout が A 点かつ B 点かつ \(\hat{q}_{\mathrm{inc}}\) を満たし、改訂用の位置差が既に通っているときに限る。

**凍結 40 画面の層。** 母集団の無作為標本ではない。次の件数を改訂用と holdout の **合計** で満たし、各層を改訂:holdout = 3:1 で割る（密な設定/データ 8→6+2、認証済みアプリ内面 8→6+2、マーケティング/ヒーロー 4→3+1、空/エラー/オンボーディング 4→3+1、残り 16→12+4）。同一プロダクトから取る画面は最大 2。ネイティブ専用、または実行時証拠が無い画面は入れない。40 枚は §2.4 の入場条件だけを使う。空状態 1 ブロックやエラー 1 フィールドだけの画面は入れない。

試行を三つに分ける。**生成不全** は帯が 3 回 \(F\) で評定に回さなかった試行。**評定不全** は 3 出力を評定し、多数決に \(F\) または \(U\) がある試行。**完了試行** は評定済みで多数決がすべて \(\{G^\star, G, G^-\}\) の試行。A と B は完了試行だけを使う。完了試行数 \(N_c\)。改訂用で \(N_c < 27\)、holdout で \(N_c < 9\) なら A/B を採択せず、先に §4.4 を見る。

**指標 A — 周辺一様性。**
完了試行の \(3N_c\) ラベルから帯割合 \(\hat{p}_k\) を取る。

1. 点推定: \(\max_k |\hat{p}_k - 1/3| \le 0.08\)（改訂用と holdout）
2. ブートストラップ（**改訂用 30 だけ**）: 完了試行を復元抽出し、各複製で \(\max_k |p_k-1/3|\) を取る。回数 2000、Hyndman–Fan 型 7、種 `20250911`。その 95 パーセンタイル \(\le 0.15\)

**指標 B — バンドル置換率。**
完了試行のうち、3 評定の集合が \(\{G^\star, G, G^-\}\) と一致する割合を \(\hat{\tau}\) とする。独立一様なら \(2/9 \approx 0.222\)。

1. 点推定: \(\hat{\tau} \ge 0.45\)（改訂用と holdout）
2. ブートストラップ（**改訂用 30 だけ**）: 同じ 2000 複製で \(\tau^\ast\) の型 7 の 2.5 パーセンタイル \(> 2/9\)

位置差は第 4 ゲートであり、**改訂用 30 だけ** に課す。\(\hat{r}_p\) は個人評定 `view[r][p]` が \(G^\star\) である割合。多数決ラベルで位置差を取ってはならない。

完了試行の個人評定について、帯 3 値の順序 Krippendorff \(\alpha\) を **報告する**。ゲートには使わない。

改訂用の採択は **A かつ B かつ \(\hat{q}_{\mathrm{inc}}\) かつ位置差**。holdout の採択は **A 点かつ B 点かつ \(\hat{q}_{\mathrm{inc}}\)**。

ブートストラップの正本は付録 C である。完了試行を凍結画面番号の昇順に並べ、`numpy.random.Generator(numpy.random.PCG64(20250911))` で試行単位の復元抽出を 2000 回する。percentile は NumPy `method="linear"`（型 7）。

**失敗時の解釈。**

| 観測 | 診断 | 直す軸 |
|---|---|---|
| \(\hat{p}_{G}\) だけ大きい | 中央崩壊。三案が同じ密度 | 範囲と驚きを帯ごとに再契約。独立生成を強制 |
| \(\hat{p}_{G^\star}\) だけ大きい | 偽の頂点、または評定者が「違う＝良い」 | テンプレ美を \(F\) に落とす |
| \(\hat{p}_{G^-}\) だけ大きい | 野心不足 | \(G\) と \(G^\star\) の契約を画面語彙で具体化 |
| \(\hat{\tau}\) が 0.22 付近 | 帯が独立ノイズ | 4 軸を帯別ファイルへ落とし、隔離生成を強制 |
| \(\hat{q}_{\mathrm{inc}}\) が大きい | フロア割れまたは評定不一致 | 手順 1 とフロア検査を強化 |

### 4.3 意図と受領の混同行列

行を \(I\)、列を \(H\) とした 3×3（\(F\) は別集計）。対角が薄いマスが、スキル改訂の対象である。

### 4.4 不全率

\[
\hat{q}_{\mathrm{inc}} = \frac{\text{生成不全} + \text{評定不全}}{N}
\]

採択の前提: \(\hat{q}_{\mathrm{inc}} \le 0.10\)。出力単位の \(F\) 率をこの記号で呼んではならない。

### 4.5 再現手順（作者チェックリスト）

1. 凍結条件を書く（改訂用 30、holdout 10、支配的表面、モデル、道具、ハッシュ、§4.2 の定数）
2. `judge-tree.md` と金標準 12 を凍結する。帯評定者 3 人が 3 ゲートを通る。ここまで生成しない
3. 生成者だけが改訂用 30 束を作る。3 回 \(F\) は生成不全として 30 に残し、評定しない。同じ顔は再生成せず、較正では評定に回す
4. 生成完了から評定へ渡すまで、生成者は after / worktree を編集しない
5. 改訂用の生成完了束をラテン方格・フロア検査付きで評定し、`scripts/toc_gate.py` を `N=30`（ブートと位置差あり）で走らせる
6. 不採択なら分岐する。
   - **本文だけ改訂**（木は凍結のまま）: スキル本文を直し、同じ改訂用 30 URL を再生成して 4 から。holdout がまだ一度も評定されていないならその URL を残し、評定はまだしない。holdout が一度でも評定済みなら、その URL は再利用禁止であり、新しい holdout 10 を凍結して手順 7 まで待つ
   - **木に注釈を足した**: §4.1 の注釈手続
7. 改訂用が 4 ゲートを満たしたら、確定木のあと **一度だけ** holdout 10 を生成・評定する（`N=10` は A/B 点推定と不全率。位置差は見ない）
8. holdout が A 点かつ B 点かつ \(\hat{q}_{\mathrm{inc}}\) を満たし、改訂用の位置差が既に通っていれば TOC を名乗る。失敗し、本文も木も変えないときは、holdout 差し替えを **最大 1 回** だけ許す。(1) 当該凍結の名乗りは無効 (2) 失敗 holdout の URL+状態は再利用禁止 (3) 新しい holdout 10 を層 3:1 が保たれるよう先に凍結 (4) 改訂用 30 の URL・生成物・評定は残し、手順 1–6 は繰り返さない (5) 手順 7 を新しい 10 に対して一度だけ行う。2 回目の失敗で、その本文の TOC 名乗りは終わる。本文を変えたら差し替え回数は 0 に戻り、改訂用からやり直す。失敗ラベルに本文を合わせて通してはならない

このチェックリストを満たすまで、「TOC スキルである」と README に書いてはならない。未較正の実装は **手法の試作** であり、較正済み成果物ではない。

## 6. 関連研究との関係

- **ヒューリスティック評価**（Nielsen & Molich, 1990; Nielsen, 1994）は欠陥の列挙である。TOC のフロアに使う。
- **デザイン批評**（Schön, 1985; Alabood et al., 2023）は質的フィードバックの型を与える。TOC は批評を 3 値帯と生成契約に圧縮する。
- **美学と HCI**（Tractinsky, 2004）は、美が意思決定に効くことを示す。TOC は美の普遍尺度を提案しない。
- **LLM-as-Judge とルブリック**（Hashemi et al., 2024）は、アンカーと人間補正を要求する。TOC の金標準 12 はそこに合わせる。
- **モード崩壊と多様性**（Zhang et al., 2025）は、典型性バイアスで出力が一つに寄ることを示す。TOC は順序付き三帯の占有を目標にする。多様だが全部 \(G\) なら不採択である。

## 7. 妥当性への脅威

**構成概念。** 三帯は日本語の日常評定に由来する。公式名を訳さず、§2 の操作的定義で評定する。

**評定者効果。** 外部 1 人を必須にする。

**画面サンプリング。** 改訂用 30 + holdout 10 の層分けは偏りを減らすためであり、母集団の無作為標本ではない。

**順序効果。** 同一の帯評定者が 3 after を順に見る。ラテン方格と位置差ゲートは平均の偏りだけを見る。相補割当で \(\hat{\tau}\) が上がり得る。各 after は木を独立に辿り、三帯の強制割当は禁止する。

**実行時の疎画面。** 点が 3 未満の画面、または同一規則の欠け / 不揃えが 3 未満の画面では \(I=G\) が \(H=G^-\) になり得る。較正 40 は §2.4 の入場 1 文だけなので、名乗りの占有対象ではない。

**エージェント / モデル依存。** 較正はモデル ID を固定して行う。

**作者汚染。** 生成者と帯評定者を分ける。

**検出力。** \(N=30\) 固定は小さい。見たあとで \(N\) を足してゲートを通してはならない。

**時間。** 視覚流行が変わると、今日の \(G^\star\) が翌年のテンプレ美＝\(F\) になる。

**倫理。** §2.1-7 により、ダークパターンと a11y 犠牲は \(F\) である。

---

## 8. 限界

- 本稿は手法の提案であり、採択データを持たない。未測定の実装を成果として扱ってはならない
- 改訂用 30 に再適合したスキルが holdout で落ちることは、想定される失敗である
- 三帯は、壊れていない改善の中での分割である。課題成功率、保持、売上は測らない
- \(G^\star\) はオンデマンドに保証できない
- ソースが git 作業樹に無い URL だけの依頼は \(R\) ではない
- ブラウザで開けない対象は、同等の実行時証拠が無い限り対象外とする
- 依頼が \(R\) でないときに TOC を適用してはならない

---

## 9. 結論

「もっといい感じにして」に対する良いスキルは、一点の最大美ではない。壊れていないことをフロアにしたうえで、**悪くない / まあまあ良い / めちゃくちゃ良い** を平均して均等に受領される 3 出力束を出せることである。

それを書く手順は短い。

1. 帯を語感ではなく、顔・横断・テーゼ・フロアで定義する
2. 1 束の意図は三帯を一つずつにする
3. 差は 4 軸の契約として書き、独立に実装する
4. 較正は改訂用 30 のあと holdout 10。ゲートを `scripts/toc_gate.py` で判定する
5. `laststance/skills` の包装規約に載せ、未較正を較正済みと書かない

実装者は §5.5 の 7 拘束を `SKILL.md` に残し、§4.5 を回す。採択の前に帯名を依頼者へ見せない。

## 付録 C. `toc_gate.py` の正本

スキル実装時、次を `scripts/toc_gate.py` に置く。較正の採択数値はこの出力だけを使う。

入力 JSON:

```json
{"N": 30, "incomplete": 2, "completed": [
  {"t": 0, "view": [["G*", "G", "G-"], ["G", "G-", "G*"], ["G-", "G*", "G"]]}
]}
```

JSON の帯記号は `G*` / `G` / `G-` だけ（本文の \(G^\star / G / G^-\)）。`t` は凍結画面番号（0 始まり）。`view[r][p]` は評定者 \(r\) が提示位置 \(p\) で付けた個人評定（木の葉だけ: `G*` / `G` / `G-` / `F`）。`U` は多数決の結果だけであり、view に書いてはならない。多数決 `labels` は入力に書かない。スクリプトが方格 \(\mathrm{BASE}[r][(p+t)\bmod 3]\) で after に集約する。`incomplete` は生成不全 + 評定不全。`completed` は `t` の昇順。\(N\ge 30\) のときだけブート条項を A/B に入れ、位置差をゲートに入れる。\(N<30\) では位置差を `ok` に入れない。

```python
# toc_gate.py — paper appendix C. numpy required.
import json, sys
import numpy as np

EPS, GAMMA, TAU0, QINC, POSD, B, SEED = 0.08, 0.15, 0.45, 0.10, 0.15, 2000, 20250911
LABS = ("G*", "G", "G-")
VIEW_OK = LABS + ("F",)
IDS = (("Ym", "Y", "Ys"), ("Y", "Ys", "Ym"), ("Ys", "Ym", "Y"))

def p_hat(labels):
    n = len(labels)
    if n == 0:
        return np.array([np.nan, np.nan, np.nan])
    return np.array([labels.count(k) / n for k in LABS])

def maxdev(ph):
    return float(np.max(np.abs(ph - 1.0 / 3.0)))

def majority(xs):
    from collections import Counter
    c = Counter(xs).most_common()
    if len(c) >= 2 and c[0][1] == c[1][1]:
        return None
    return c[0][0]

def labels_from_view(t, view):
    buckets = {"Ym": [], "Y": [], "Ys": []}
    for r in range(3):
        for p in range(3):
            buckets[IDS[r][(p + t) % 3]].append(view[r][p])
    labs = [majority(buckets[k]) for k in ("Ym", "Y", "Ys")]
    if any(x is None or x not in LABS for x in labs):
        raise ValueError("completed trial has F/U/tie; move to incomplete")
    return labs

def check_trial(row):
    view = row["view"]
    if "t" not in row:
        raise ValueError("t required")
    if len(view) != 3 or any(len(x) != 3 or any(v not in VIEW_OK for v in x) for x in view):
        raise ValueError("view must be 3x3")

def main(path):
    d = json.load(open(path))
    N = d["N"]
    trials = sorted(d["completed"], key=lambda r: r["t"])
    ts = [r["t"] for r in trials]
    if len(ts) != len(set(ts)):
        raise ValueError("duplicate t")
    if d["incomplete"] + len(trials) != N:
        raise ValueError("incomplete + completed must equal N")
    for t in trials:
        check_trial(t)
    qinc = d["incomplete"] / float(N)
    nmin = int(np.ceil(0.9 * N))
    q_ok = qinc <= QINC
    n_ok = len(trials) >= nmin
    if not n_ok:
        json.dump(
            {"ok": False, "q_inc": qinc, "A": None, "B": None, "pos": None},
            sys.stdout,
        )
        return
    packed = [labels_from_view(t["t"], t["view"]) for t in trials]
    labs = [x for row in packed for x in row]
    ph = p_hat(labs)
    tau = float(np.mean([set(row) == set(LABS) for row in packed]))
    views = np.array([t["view"] for t in trials])
    r = np.mean(views == "G*", axis=(0, 1))
    posd = float(np.max(r) - np.min(r))
    use_boot = N >= 30
    pos_ok = True if N < 30 else posd <= POSD
    a_ok = maxdev(ph) <= EPS
    b_ok = tau >= TAU0
    if use_boot:
        rng = np.random.Generator(np.random.PCG64(SEED))
        nc = len(trials)
        idx = np.arange(nc)
        md, tb = [], []
        for _ in range(B):
            take = rng.choice(idx, size=nc, replace=True)
            sl = [packed[i] for i in take]
            md.append(maxdev(p_hat([x for t in sl for x in t])))
            tb.append(np.mean([set(t) == set(LABS) for t in sl]))
        a_ok = a_ok and float(np.percentile(md, 95, method="linear")) <= GAMMA
        b_ok = b_ok and float(np.percentile(tb, 2.5, method="linear")) > 2.0 / 9.0
    ok = q_ok and n_ok and a_ok and b_ok and pos_ok
    json.dump(
        {
            "ok": bool(ok),
            "q_inc": qinc,
            "p": ph.tolist(),
            "tau": tau,
            "posd": posd,
            "A": bool(a_ok),
            "B": bool(b_ok),
            "pos": bool(pos_ok),
        },
        sys.stdout,
    )

if __name__ == "__main__":
    main(sys.argv[1])
```

NumPy `method="linear"` は Hyndman–Fan 型 7 である。`krippendorff` はゲート α 専用であり、本スクリプトには含めない。

## 付録 D. `toc_alpha.py` の正本

帯 9 件の \(\alpha\) ゲートだけに使う。`krippendorff==0.8.2` をピンする。

入力: 行 = 評定者 3、列 = 帯金標準 9。値は `0` (`G-`), `1` (`G`), `2` (`G*`)、欠測は `null`。

```python
# toc_alpha.py — paper appendix D.
import json, sys
import numpy as np
import krippendorff

def main(path):
    data = np.array(json.load(open(path)), dtype=float)
    a = krippendorff.alpha(
        reliability_data=data,
        level_of_measurement="ordinal",
        value_domain=[0, 1, 2],
    )
    json.dump({"alpha": float(a), "ok": bool(a >= 0.67)}, sys.stdout)

if __name__ == "__main__":
    main(sys.argv[1])
```
